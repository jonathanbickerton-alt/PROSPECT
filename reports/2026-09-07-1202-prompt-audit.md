### (a) RITUAL — emphasis or repetition with no measured failure behind it

Only three items qualify, and two of them are structural decay rather than
rhetoric. **This is the smallest category, and that is the audit's main result.**

**R1 — `qa-tester.md`: the standards' numbering and placement (F4).**

**R3 — `report-writing/SKILL.md`: the description's trigger enumeration (F6).**

This is the one genuine judgment call in the category, and I want to be careful
because the underlying rule is emphatically CONTROL — four conditional forms
leaked, and the working agreement records the cost. **The rule stays. What is
ritual is where its history lives.**

A skill `description` is loaded on every request. This one carries ~200 words,
of which the operative part is the last sentence and the rest is the argument
for it. The guide's Group 3 note that trigger text may legitimately carry
calibrated urgency covers the *urgency*; it does not require the *archaeology*
to ride along.

*Proposed replacement description (the control preserved, the history moved to
the body, where it already exists nearly verbatim):*

> Use when writing any session report, gate report, diagnosis, or verification
> report to `reports/`. Covers the filename convention, the FOR ADVISOR block,
> and the command that sources the timestamp. **Trigger unconditionally, on
> every session, whatever it does** — build, merge, diagnosis, state check, a
> single lookup, or a session that answers a question and stops. There is no
> read-only exception and no triviality exception. The skeleton is the
> session's FIRST ACTION and is filled at close; a three-line report is a valid
> report, and a skeleton left with placeholders is a valid diagnostic.

That is 88 words against ~200 and loses no instruction — only the enumerated
list of state-changing verbs (already restated in the body) and the sentence
explaining that four conditional forms were tried (also in the body, twice).

**If Jon prefers, this is the one to decline.** The enumeration is cheap
insurance on a rule that has demonstrably leaked four times, and "it costs
tokens" is the weakest reason in the audit's own hierarchy.

**C1 — the guard-traps concurrency rule (F1). KEEP THE RULE; FIX THE FILE.**

This is the highest-value finding in the audit, because the three copies
disagree and a session obeying the wrong one is punished either way.

*The control and its provenance:* a qa-tester run started a second guard-traps
instance after the first exceeded a foreground timeout, stranded mutations in
`buildPanelRowsFromStore` and `viewFilter.ts`, and reported a harness artefact
as a finding. Recorded in `regression-guard.md` and `qa-tester.md`. Working
agreement §4 carries the general form.

*The defect:* `regression-guard.md` and `qa-tester.md` were **amended
2026-08-09** with an unusually clear-eyed piece of reasoning —

> "the rule first said 'never in the background', and two consecutive gates
> backgrounded it anyway because the run exceeds the 120s foreground timeout and
> the harness moves it there. Both were correct to… **A rule that forbids the
> only workable way to run the thing gets ignored, and an ignored rule stops
> protecting the part that matters.**"

`session-close/SKILL.md` never got that amendment. It still reads:

> "Never run `guard-traps` concurrently **or in the background**: it mutates
> tracked source…"

and its instrument block still says `# once, foreground`.

*Why this is not academic:* **this session backgrounded guard-traps twice** — on
2026-09-06 for the 165-trap run and again for the 167-trap run — waiting for
each single instance to finish. That is exactly what the amended rule
prescribes and exactly what `session-close` forbids.

*Proposed diff — `session-close/SKILL.md` §1, replacing the one-line rule:*

```diff
-Never run `guard-traps` concurrently or in the background: it mutates tracked
-source, and overlapping runs have left a mutated file in the tree.
+Never run a SECOND `guard-traps` instance while one is in flight, and let
+nothing else read the tree while it runs — it mutates tracked source, and
+overlapping runs have left a mutated file in the tree. Backgrounding a single
+instance is fine and is usually necessary: the run exceeds the 120s foreground
+timeout. Start one, wait for it, then run everything else. (Amended 2026-08-09
+in regression-guard.md and qa-tester.md; this file was missed.)
```

*and §2's instrument block:*

```diff
-npm run guard-traps       # once, foreground — expect N/N caught
+npm run guard-traps       # ONE instance; background it and wait — expect N/N
```

**C3 — the suite enumeration (F3a). KEEP THE RULE; THE INSTRUMENT CHANGED.**

The control is real and its provenance is precise: a `[a-z-]` character class

`npm run suite` was committed at 1602 precisely to end hand-enumeration — it


## Item 3 — the model question

**A proposal, explicitly not a decision.** Nothing here should be read as a
recommendation to switch models.

### What the audit's findings imply about brief shape on a frontier model

The audit's central negative — no dated idioms, minimal pressure language,
almost everything traceable to an incident — means **the briefs are not carrying
model-era cruft, and shortening them is not the lever.** What the findings *do*
suggest, per session type:

**True-state (read-only inventory) sessions.** These are the briefs that already
work best: they name the surface, forbid source changes, and ask for questions
rather than answers. The audit found nothing to change in how they are shaped.
The one implication is F2's: a true-state session's value is entirely in what
survives compaction, and the compact instruction currently points at a file that
does not exist. Fix that before anything else.

**Build sessions.** These carry the most prescriptive scaffolding — SHED ORDER,
NEVER SHED, the affordability line, per-item decomposition. The guide's Group 1c
would normally read `ITEM 1 … ITEM 5` decomposition as over-specification. **It
is not, here**, and the evidence is in this week's own reports: the REQ-D6-01
brief's decomposition is what made the pricing-self-exclusion finding
reportable-instead-of-buildable, and the SHED ORDER is what let two items be
dropped without a negotiation. On a more capable model the *decomposition*
should stay; what could relax is the **step-level prescription inside** an item
(the guide's "state outcomes and how to verify, not the method"). A trial worth
running: hold Items 1-2 fully specified and give Item 3 as an outcome plus its
verification, and compare what comes back.

**Docs sessions.** Shortest briefs, least room for model difference. The audit
implies one change unrelated to model: a docs session that commits a supplied
file should state up front whether byte-identity must be verified, because the
v3.3.14 session could not and had to record that as a Limit.

**Walk reconciliation.** Not exercised this week; the audit surface says nothing
about it. I decline to speculate.

### What would be measured to compare Fable 5.1 against Opus on the same brief

The honest framing is that **one brief run twice is an anecdote**, and this
project's own standards (qa-tester 10, 11) would reject it: a comparison with no
baseline showing the measurement has teeth is measuring nothing. So the proposal
is a design, not a run.

**Design.** Pick **three** briefs of the same type — build sessions are the only
type with enough volume — from the archive, ones whose outcome is already known
and gated. Re-run each on both models from the same BASE, with the same brief
text, and with the session's own gate as the grader. That gives 6 runs and a
known-correct answer per brief, which is the baseline the comparison needs.

**Report quality** — graded by the project's own instruments, not by reading:
- gate outcome (guard-traps N/N, suite N/N, tsc) — pass/fail, the primary;
- **traps planted and caught**: did the run produce traps that go red by hand?
- **findings-not-builds**: did it report the pricing-self-exclusion class of
  finding, or build past it? This is the single behaviour most worth measuring
  and the hardest to fake;
- FOR ADVISOR conformance: ≤25 lines, `Repo:` present, `Certifies:` names a hash;
- **vacuous-check rate**: how many checks in the produced spec pass on a planted
  violation. The most diagnostic number of the six.

**Tokens** — input and output per run, from `response.usage`, split by phase
(build vs gate vs close). Cost per *completed, gated* session is the figure, not
cost per request: a cheaper run that needs a second session is not cheaper.

**Wall time** — start to pushed commit, with the guard-traps run timed
separately, since it dominates and is model-independent.

**Two cautions.** Fable 5.1's own guidance says prompts written for prior models
are often *too prescriptive* and reduce its output quality — so a fair trial
must run at least one arm with the relaxed-Item-3 brief above, or it measures
the brief and not the model. And these briefs are long-horizon agentic work,
which is where effort settings matter most; a comparison at mismatched effort
tells you nothing.

**Cost.** Six gated sessions is roughly six times a normal session's spend, and
the guard-traps runs alone are ~15 minutes each. That is the number Jon should
weigh the proposal against, and it is why this is a proposal.
