## Item 1 — three claims checked against source

### Check 1 — `isEventOn` is the only reader of `.enabled`

**MATCH where the pin reaches; the document's wording is looser than the pin.**

`src/utils/forecasting.ts` holds exactly four code reads, which is what the
spec asserts:

```
401:   Enabled: e.enabled === false ? 'No' : 'Yes',     export writer 1 (market)
1081:  Enabled: e.enabled === false ? 'No' : 'Yes',     export writer 2 (pricing)
1350:  Enabled: e.enabled === false ? 'No' : 'Yes',     export writer 3 (yield)
4206:  if (e.enabled === false) return false;           isEventOn itself
```

plus two comment lines at 4187 and 4191 that name the field in prose.
`WhatIfTab.tsx` and `scenarioHelper.ts` are both **zero**, which is the half
that matters — those are the two engines.

**The caveat, stated because a report that only confirmed the claim would be
less useful than one that says where it stops.** `EventsSummaryTable.tsx`
reads `r.enabled` four times (109, 114, 123, 124). Those are **not** reads of
an event carrier's field: `r` is an `EventSummaryRow`, a derived row whose
`enabled` is set by `isEventOn(e)` in the three builder loops in
`forecasting.ts`. So the predicate is still the only thing that decides, and
the summary table is reading a decision already made rather than making a
second one.

But v3.3.14 §1 says "zero reads of `.enabled` elsewhere", and read literally
across `src/` that is not true. The pin as implemented covers the three engine
files, and it should be read as *zero reads that constitute an apply decision*.
Worth tightening in the next revision — the sentence claims more than the
check delivers, and the gap is exactly the kind that a later session would
trust and be wrong about.
