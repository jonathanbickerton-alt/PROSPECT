## 1. What the card does now

| settled semantic | how it is wired |
|---|---|
| typed target constrains the sliders | `achievableTargetRange`, shown as `Reachable: lo – hi` |
| unreachable target flagged, not clamped | `solveForTarget`'s blocked arm, with the **binding member named** |
| moving a slider rebalances the rest | `rebalance`, with the current lock set passed in |
| padlocks hold | manual only; the padlock click is the **only** writer of lock state |
| a collapsed range locks | every slider disabled, with copy saying the constraints left one value |
| blank target = free sliders + live blend | blank is a real state and carries no verdict at all |
| live blend | `blendedArpu`; **null renders as "not known"**, never `0.00` |

**The two causes of a frozen slider are kept apart.** A slider disabled because
the user held it and one disabled because the range collapsed are different
claims, and the padlock reflects only the first. Collapsing them would make the
control assert the user held something they did not.

## 2. The two collapses, done loudly

### `blendTierMix` → `blendedArpu`, and why it had to be renamed

Changing the return type from `number` to `number | null` produced **exactly
zero compiler errors**. This tsconfig sets no `strict`, so `strictNullChecks` is
off and `null` is assignable to `number`: the nullable return enumerated
nothing, protected nothing, and left both call sites treating absence as a
number. That is the `seedBaseVolume: number | null` lesson from the seed-or-
decline arc, repeating exactly.

So the absence carrier is the **name** — `blendTierMixOrNull` — which the
compiler does check. Every call site had to be touched to keep compiling, and a
future caller cannot reach the function without reading `OrNull` first. Same
move as `Seed_Base_Known`: when the type cannot hold known-ness, something else
must.

**The `?? 0` was not only a display bug.** Its two call sites sit on opposite
sides of the read/write line:

- the promo card's blend **display** showed a number quietly too low;
- `buildPromoEvents` used the same value as the saved event's `arpu` and to
  compute its `revenue` — so the contaminated figure was **written into the
  saved event** and outlived the session.

A member with an unknown ARPU did not read as missing. It read as a real and
very cheap member. The card now refuses to build the event at all.

### `autoBalanceMix` → `rebalance`, and the one difference that mattered

A thin delegation with an empty lock set, pinned equal to `rebalance` across 400
randomised cases before the collapse. It keeps its name and signature because it
has **two** callers and only one is the promotion card — the **Value tab's
yield-event mix** still uses it, which is a live control outside this session's
stated surface.

Stage 2 found a genuine behavioural difference: the old body would write a share
for a tier not yet present in the mix, and `rebalance` calls that malformed and
refuses. It rated the reachability "apparent, not proven unreachable". That is
reason to close it, not to argue about it — `autoBalanceMix` now seeds the
missing tier before delegating, restoring the old behaviour exactly, with a spec
case pinning it.

## 3. Write enforces, read tolerates — mounted, both directions

The card cannot save a mix that fails `conformsToTotal`, nor one whose blend is
absent. Both are refusals rather than repairs: the engine conforms shares it
*produces*, but a mix the user has left non-conforming is theirs to resolve, and
rewriting it on save is the tool stating something on their behalf.

Read stays tolerant. A restored mix summing to 90 loads **exactly as saved** and
is flagged amber — never silently normalised. The spec drives that through the
**real restore path**: a saved promotion with a non-conforming stored mix, opened
by clicking the card's own edit control. A probe that set the draft mix directly
would inherit my assumption about how restore works, which is the mistake the
Base-series arc made five times before the real path was driven.

### A vacuous check I wrote, and the control that caught it

My first write-enforcement check asserted "no save control is enabled" with a
non-conforming restored mix. It passed. The anti-vacuity control beside it — the
same mount with a **conforming** mix, asserting the save controls **are**
enabled — **failed**, which meant the first check had been passing for the wrong
reason: my stored mix set two members while the card derives three, so the third
carried no share at all and the mix was non-conforming for a reason unrelated to
the total. Guessing member names from the raw fixture column instead of reading
the ones the card derives is "model the path instead of driving it" in miniature.
The spec now reads the member names off the card's own padlocks.

### A spec that hung on success

`spec:mix-card` ran for ten minutes and produced an empty output file. The 27
checks had already passed; `report()` only called `process.exit` on failure, and
JSDOM's timers keep the event loop alive forever after a green run. Every other
mounted spec in the directory exits unconditionally. **A spec that hangs on
success is indistinguishable from one that hangs on a defect**, which is why the
convention exists.

## 5. The first behavioural fixture — and a deviation from the brief

The brief said to **commit the exported save under `test-data/`**. It is not
committed, deliberately, and this is the one instruction I did not follow as
written.

`.gitignore:15` excludes `/test-data/*.xlsx`; no `.xlsx` is tracked anywhere in
this repo; and the fixture convention requires regeneration through a committed
deterministic builder and forbids hand-made fixtures. The brief said "with
provenance **per fixture-handling**", so the convention governs. What is
committed is `scripts/build-promo-mix-fixture.mjs` — the same behavioural case,
reproducible from a fresh clone, which a gitignored binary would not be.

**The mix is solved by the engine, not written by hand.** The builder calls
`solveForTarget` with High Value held at 40 and a typed target of 26, giving
`{Low 33.333…, Mid 26.666…, High 40}`. So the fixture records a state the card
could actually have produced; a hand-written mix would be a guess about the
engine's output wearing a fixture's clothes. The builder self-checks
conformance, blend-equals-target and held-member-unmoved, and exits non-zero
rather than emitting a fixture that fails the invariants it exists to show.

`spec:event-roundtrip` gained 8 behavioural checks (39 → 47) and **fails loudly**
when the fixture is absent rather than skipping — stage 3 verified that by moving
the file aside. A behavioural case that disappears with its fixture is how a
suite reports green while testing less than it claims.

## WALK INSTRUCTIONS — the three things your eyes gate

Step 2 → **Promotion** card → tick **Mix**. The value axis gives three bands.

**1. The padlock feel.** Drag a slider and watch the other two move. Then check
the padlocks: **none of them should have engaged.** That is the decision you took
today — moving a slider must never hold it. Now click a padlock, drag a
*different* slider, and confirm the held one does not budge. Click it again to
release. The question to bring back: does manual-only feel like control, or does
it feel like extra work? If it is the second, that is the auto-lock question
returning, and it is worth putting to Alessandro with your own reaction attached.

**2. The unreachable flagging.** With one band held, type a deliberately silly
target — 999. You should get an amber line naming **which band forms the wall and
where the wall is**, and the mix should not move at all. Check specifically that
your number was **not** quietly changed to the nearest reachable one. Then type
something inside the stated `Reachable:` range and press **Apply**: the blend
shown underneath should land on exactly what you typed.

**3. The amber tolerance.** This one needs a saved session. Open a promotion whose
mix does not total 100. It should load **exactly as saved**, with the sum amber —
not silently corrected to 100 — and the Add/Save button should be **disabled**
until you fix it yourself. The tool flags; it does not repair on your behalf.

**Also worth a glance:** if a band has no ARPU, the blend line reads *"not known"*
rather than `0.00`. That distinction is the reason the save path changed, so if
you can reach it, it is worth seeing once.
