## Item 1 — CRASHED as its own state

`specFails` returned a boolean read off the exit code, which is precisely WHY a
crash and a failed assertion were the same event. It becomes `specVerdict`,
returning `green` / `failed` / `crashed`, and `specFails` survives as a
one-line wrapper (`verdict !== 'green'`) so the positive control — which only
ever cared "is this spec red at all" — keeps its exact prior meaning.

`failed` requires a line matching `/^\s*FAIL/m` in **either stream**: specs
print FAIL lines to stdout, a dying spec prints a stack to stderr, and reading
one would misclassify whichever a future spec chose. No `\b` after `FAIL`, on
purpose — specs here print `FAIL`, `FAILED` and `FAILURE`, and all three are an
assertion reporting.

### The classifier has its own control, and it earned it immediately

A CRASHED/CAUGHT distinction that silently degraded to "everything is CAUGHT"
would restore the exact defect it was built to end, **invisibly** — every trap
still CAUGHT, the gate still green. So both classifications are exercised on
every run, before any trap is planted, against fixtures written to produce
them: a throwing spec must read `crashed`, a FAIL-printing spec must read
`failed`. The fixtures go to the OS temp dir, never `scripts/`, so they cannot
become untracked clutter or be swept up by the suite runner.

It caught two defects in the implementation, the second serious:

1. `require` in ESM scope — the harness crashed outright. Loud, harmless.
2. **The regex contained a literal backspace byte.** `/^\s*FAIL\b/m` was written
   through a heredoc; `\b` is a valid escape in Python *and* in regex meaning
   different things, so Python turned it into `0x08` and the pattern demanded a
   backspace after "FAIL". It could never match, so **every trap would have
   been reported CRASHED** — and I would have written a report announcing that
   the entire 139-trap registry was catching by crash. Precise, dramatic, and
   entirely false.

That is this session's own subject reproduced inside its fix: a boolean cannot
tell a crash from an assertion, and a regex that never matches cannot tell an
assertion from a crash. Neither announces itself.

## Limits of this check

- **72 and 90 are diagnosed, not repaired.** Both still die rather than report
  when their mutation lands, so both still count as not-caught. Their FAIL
  lines, if any exist behind the crash, are unknown — 102 turned out to have 42.
- **The CRASHED census is one run on one tree.** A spec that crashes only under
  some other trap's mutation would not appear in it.
- **`FAIL` is a text convention, not a contract.** A spec that reported failures
  without a line starting `FAIL` would be classified CRASHED. Every spec in the
  suite uses it today; nothing enforces that they keep to it.
- **The global class is exercised by exactly one trap.** Trap 22 is its only
  member, so the class's own behaviour under, say, a count of 3 is untested.
- **Item 3's new check asserts the SHAPE of a correct churn add** (three rows,
  churn fields, non-zero volumes), not the trajectory — the existing R7 checks
  already own the numbers.
- **The Overall door's checks are STRUCTURAL, like the ones beside them.** They
  read source text; nothing here mounts the Overall door and drives it into the
  blocked state.
