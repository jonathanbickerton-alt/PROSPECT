| `outflowArpu` | **fitted** | `:2293, 2299, 2316` |

### Base ARPU — yes, it is a real quantity

The brief asks whether a base ARPU exists at all, given that base volume is
derived from the seed. **It does, and it is the most carefully handled of the
four.**

- **Historically** it is read directly: rows carrying the Base metric contribute
  `subs` and `rev` to `baseAcc`, and `baseArpu = ba.rev / ba.subs`
  (`App.tsx:2645, 2652`). Base is a *read* metric in the source data even though
  base *volume* in the forecast is derived — so there is a real numerator.
- **On aggregation** it is weighted by the **derived running base stock**, not
  by inflow (`forecasting.ts:2637`), with the reasoning recorded at `:2565`:
  *"Weighting a base-ARPU blend by acquisition volume answers a different
  question — it asks what the newly-acquired are worth, not what the installed
  base is worth."* The recursion is floored at zero because a negative weight
  once produced a negative baseArpu (`:2578-2583`).

**So base revenue is well-defined**: `baseArpu × base volume`, where base volume
is the derived stock the chart already computes as `Base (Baseline)` /
`Base (Adjusted)`. Nothing needs inventing.

### Where they are read today

- `ForecastVsActualsTab` (**Step 3**) renders **all four as first-class series**
  — colours at `:106`, labels *Inflow ARPU / Outflow ARPU / Retention ARPU /
  Base ARPU* at `:114`, row type at `:243`. The pattern the grid needs already
  exists in the app, one tab over.
- The Step-2 chart reads **one** of them, `outflowArpu`, as a display-only
  reference line.
- `computeAdjustedForecast` reads `retentionArpu` once, inside the yield blend
  (`WhatIfTab.tsx:1169`).

## 2. The blended chart line — and the finding that explains D1-02

### `ARPU (Baseline)`

`WhatIfTab.tsx:1277` — `m.baseline.arpu`, i.e. the forecast month's blended
`arpu.mean`. Trace it back and it has **two different denominators depending on
whether the cohort is a leaf or an aggregate**:

| Level | Formula | Denominator |
|---|---|---|
| **Historical / leaf** | `totalRev / totalSubs` (`App.tsx:2646-2648`) | inflow + outflow + retention + **base** |
| **Derived aggregate** | `arpuOf(ms, m => m.arpu, …)` (`forecasting.ts:2630`) | inflow + outflow + retention — **base excluded** |

Both are Σrevenue/Σvolume, honouring the settled rule. But they are Σ over
**different scenario sets**, and the same column name carries both.

### `ARPU (Adjusted)`

`WhatIfTab.tsx:1278` — `pricingARPU`, the end of a three-pass blend. The load-
bearing line is `:1191`:

```ts
blendedARPU = (basePool × baseARPU + Σ pool.size × pool.arpu) / newBAdj
```

**Its denominator is `newBAdj` — the adjusted BASE STOCK.** It is a
revenue-per-installed-subscriber figure.

Its anchor is `baseARPU = m.baseline.arpu` (`:1136`), which is why adjusted
equals baseline exactly when no events apply — the comment at `:1132` names
that as deliberate ("Option A"). Once events exist, the figure is re-weighted
over base stock.

### `ARPU Outflow (Ref)`

`:1280` — `baseForecast.months[idx]?.outflowArpu?.mean ?? m.baseline.arpu`.
**Baseline only, display-only, no adjusted counterpart**, with a blended
fallback when the band is absent.

### Why this is D1-02

Three denominators sit under two chart lines the user reads as one measure:
flows+base (leaf baseline), flows-only (aggregate baseline), base stock
(adjusted). **Revenue cannot be read off the chart as ARPU × volume**, because
which volume depends on which line and which cohort level. That is the defect
behind the finding, and it is a definition problem before it is a UI problem.

## 4. The adjusted path, per event kind

How each kind moves per-scenario volume and ARPU, and whether per-scenario
adjusted revenue is therefore well-defined.

| Kind | Volume effect | ARPU effect | Per-scenario revenue well-defined? |
|---|---|---|---|
| **Market (volume)** | Pro-rated into the targeted scenario; `m.uplifted.*` | Event pools carry their **own** ARPU, `pool.arpu = event.revenue / event.subscriberVolume` (`:1189`) | **Yes.** The pool holds revenue directly. Scenario is the event's `scenario` field. |
| **Yield (rate)** | none | Shifts the retained cohort's effective ARPU; not pro-rated (`:1141-1145`) | **Yes for Retention.** The code already reads `retentionArpu` as its anchor. Other IBRO targets are filtered out at `:1147` — only `ye.ibro === 'Retention'` reaches this blend. |
| **Pricing (rate)** | none | Applied after yield; scoped by `target` (cohorts / cohorts+base / base-only) and `cohortScope` | **Partly.** `target` and `cohortScope` already name which pool the price touches, so the mapping to scenarios exists — but it is applied to the *blended* figure, not per scenario. |
| **Churn (outflow volume)** | Reduces outflow by the stored delta | none directly | **Yes**, once outflow ARPU is carried: revenue = outflowArpu × adjusted outflow. |
| **Dilution** | none — "retention volume is assumed unchanged" | Moves **retained revenue only** | **Yes, and it is the cleanest case** — it is definitionally a revenue-only move on the Retention scenario. |

### The one that is NOT well-defined

**Yield on Inflow, Outflow or Base.** The blend at `:1147` filters
`ye.ibro !== 'Retention'` and returns false, so a yield event targeting any
other scenario reaches no ARPU blend on this path. Whether that is by design or
by omission is a question for the build session — but a Revenue row that claims
to show yield effects would be silent for three of the four scenarios today.

**And the structural one.** Every kind above collapses into `blendedARPU` over
`newBAdj`. There is no per-scenario adjusted ARPU anywhere in the pipeline to
read; producing one means carrying four blends instead of one through passes
E and F. That is the engine work, and it is the bulk of the estimate.

## 5. Timing — the T+1 lag on Base

`WhatIfTab.tsx:920-921`:

```ts
newBBase = max(0, p_bBase + p_prevBBaseIn − p_prevBBaseOut)
newBAdj  = max(0, p_bAdj  + p_prevBAdjIn  − p_prevBAdjOut)
```

Base at month *t* is built from **month t−1's** flows.

**What it implies for a Revenue row.** On any chart month, the three flow
revenues describe **that month's** movements while base revenue describes a
stock that reflects flows **through the previous month**. They are correct
together and they are not additive into a "total revenue for month t" without
saying which convention is meant — a flow event in month *t* shows in flow
revenue at *t* and in base revenue at *t+1*.

This is the existing documented Base semantics, not a new problem; but a
Revenue measure makes it visible in a way the Volume row already does and
nobody has queried.

## 7. Cost

### Mount reach

**`chartData` is a pure seam.** `computeAdjustedForecast` is an exported pure
function taking plain arguments — the pricing sessions exercised exactly this.
So the *data* half needs no mount: a pure spec can assert per-scenario revenue
and ARPU columns against hand-written literals, the way `spec:churn-fold` does
for the fold.

The mount is needed only for the **control row** — that the scenario buttons
multi-select within a measure, that the measure row is single-select, and that
switching measures re-keys the chart. `spec:mix-card` already mounts
`WhatIfTab` with a real provider, and `spec:compare-render` (40 checks) already
covers chart drawability. Neither needs new infrastructure.

### Locale strings

New strings: the measure row (**Volume / Revenue / ARPU**) and the scenario row
(**Inflow / Base / Retention / Outflow**), plus whatever the axis and legend
need — of the order of **8–12 keys**.

**They must be added in all six locales, translated.** The 1924 report found
**50 of 76** guide-quoted keys already byte-identical to English across
de/es/fr/it/pt — including `whatif_volume`, `whatif_value` and `whatif_pricing`,
the very tab labels this control sits beside. Adding English-only strings would
deepen a gap that is already a queued session, and would put untranslated new
labels next to untranslated old ones.

### Session estimate

**(a) Chart seam only — baseline per-scenario Revenue and ARPU: one session.**
Copy the four bands into `chartData`, derive revenue as ARPU × volume, add the
control row, spec the columns with literals, two traps. Adjusted cells would
show baseline values or an explicit absence — which is a decision, not a
default.

**(b) Engine + chart — baseline and adjusted: two to three sessions.**
Session 1 carries four ARPU blends through passes E and F instead of one, with
the pricing/yield/dilution scoping mapped per scenario, and resolves the
yield-on-non-Retention gap. Session 2 does the chart seam and control as in (a).
A third is likely for the Base cells and the reconciliation checks, depending
on the decisions below.

**Not included:** Scenario Compare (a second engine), export columns, Overall
Forecast. Each is its own scope.

## DECISIONS NEEDED

**1. Base cells — what does Base × Revenue mean on a chart month?**
The quantity exists (`baseArpu` × derived base stock), but it is a **stock**
figure sitting beside three **flow** figures, and it lags them by one month
(§5). Options: show it and label the lag; show it only in the ARPU measure and
leave Revenue blank for Base with a stated reason; or omit the Base row from
Revenue entirely. This is a product call, not a technical one — all three are
buildable.

**2. The blended line's fate.**
Today's `ARPU (Baseline)` and `ARPU (Adjusted)` have different denominators
(§2), and `ARPU (Adjusted)` is load-bearing for the pricing card (§6). Options:
keep it as a fifth "Blended" scenario button; retire it from the chart and keep
it internal to pricing; or redefine it — which needs its own decision because it
moves stored pricing baselines.

**3. Scope beyond Step 2.**
Scenario Compare runs a second engine with no per-scenario ARPU. Does the grid
stop at Step 2 for UAT, or is Compare in scope? Step 3 already has all four
series, so it needs nothing.

**4. Export.**
Does the export gain per-scenario Revenue and ARPU columns, and if so does that
change the sheet's shape for files already in circulation? The export currently
writes blended only.

**Also for the record, not a decision:** the historical/aggregate denominator
split in §2 is either a deliberate convention with two meanings or a defect. I
have not judged it — it predates this session and correcting it would move
figures. It needs an answer before a Revenue row is built on top of it.
