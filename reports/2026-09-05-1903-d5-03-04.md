## Item 1 — D5-03: confirmed, and worse than the screenshot

### The read-set of the restore, measured

`handleEditPromoStart` (`:4133`) restores **19** fields — the seven scope dims,
date, volume, contract length, campaign, comment, target, mix enabled/axis/draft,
band rates, locks, target ARPU, the pricing arm, and the dilution pair.

**`amountType` is not among them.** `setPromoAmountMode` had exactly **ONE**
writer in the whole file: the toggle button itself (`:7134`). Neither edit path
set it, and `resetPromoDraft` did not clear it.

### It is not a display defect

`handleSavePromoEdit` passes `promoAmountMode` straight into
`buildPromoEvents`. So reopening a `+10%` promotion with the control left on
Subs and pressing **Save Changes without touching anything** rewrote the event
as **ten subscribers**. A hundred-fold change of meaning, silent.

Measured by planting exactly that:

```
D5-03 pct edit   %-pressed false  subs-pressed true  volume 10
                 written [["absolute",10]]
```

The screenshot was the mild half.

### Three faults from one gap

| | consequence |
|---|---|
| no restore on the single-row path | the control shows a stale mode — the screenshot |
| the save re-emits that mode | **a percentage promotion is converted to absolute** |
| no clear in `resetPromoDraft` | the mode **leaks into the next** promotion |

### The Volume card has always done this

`setStoredAmountControl(event.amountType === 'percentage' ? 'pct' : 'subs')`
(`:3632`), and it writes that control at **eight** sites — restore, resets and
churn switches. The promotion card wrote its own at **one**. This is the third
inline amount-mode control that v3.3.11 §1 records and that the 1526 session
shed the extraction of; the cost of that shed has now been paid once.

### The fix

Restore in **both** edit paths (single and campaign — every row of a campaign
is built by one `buildPromoEvents` call, so the first row speaks for the group,
the same assumption the mix and pricing arm already make), and clear in
`resetPromoDraft`.

**And the dependency arrays.** All three promo builders
(`handleAddPromotionEvent`, `handleSavePromoEdit`, `handleSavePromoCampaign`)
read `promoAmountMode`, `promoMixLocked`, `promoDilutionCurrent` and
`promoDilutionTarget`, and **none declared any of the four**. It happened to
work because `newPromo` is listed and every restore also sets it — which is
precisely the shape D3-04 exists to stop this codebase relying on. Four names
added to each of the three.

### Mounted, through the card

```

                 written [["percentage",10]]
D5-03 abs edit   %-pressed false  subs-pressed true

```

Driven through the real pencil and the real Save Changes, with a capturing

**Two false starts, both fixed.** My first drive took "the last button in the
row", which is **Delete** — an empty write list that the assertions read as a
failed restore, so a wrong control looked exactly like a broken one. The pencil
now carries `promo-row-edit-<id>`. And my "did it open" guard tested for the
unit control, which is **always mounted** as part of the add form; it now tests
for the Save Changes button, which exists only while an edit is open.

## Item 2 — D5-04, measured only. Nothing built.

### (a) Which handler the Volume pencil calls

`WhatIfTab.tsx:6118` → **`handleEditStart`** (`:3558`), the Volume form's
handler, with no promotion branch. The promotion's own `handleEditPromoStart`
is reachable only from the Promotion card's table.

### (b) What a no-change save from the Volume form writes

Driven mounted on a percentage Retention promotion with a value mix, a stated
band rate and a lock: edited from the Volume table, **nothing changed**, saved,
and confirmed through `EventChangeConfirmModal`.

```
D5-04 committed  yes
D5-04 changed fields: arpu, retentionLinked
    arpu: 36 -> 0
    retentionLinked: undefined -> true
```

| | result |
|---|---|
| `promoMix`, `promoBandArpuOverride`, `mixLocked`, `promoRebanded`, `promoPricingMode/Amount`, dilution pair | **PRESERVED** |
| `arpu` | **36 → 0** |
| `retentionLinked` | absent → `true` (normalisation) |

**Partially kept.** The structured arms survive because the Volume save is a
**patch spread over the original** (`{ ...e, ...patch }`) and `patch` names 22
fields, none of them promo arms. What it does not spread is the **rate**:
`draftEventRate` returns `arpu: 0` for a percentage event — right for a plain
percentage volume event, which states no rate, and wrong for a promotion whose
rate **is** the mix blend. With `revenue` already 0, the pool falls back to the
month's baseline and the re-banded rate is silently lost.

**The measurement nearly reported nothing.** My first drive did not commit —
the confirm modal's button reads exactly **`Save`**, not "Confirm". A check
that the save *actually committed* sits in front of the comparison, so the run
reported a failed drive instead of a triumphant "nothing changed".

### (c) Both tables list the same row

The Volume table maps `marketEvents` with **no `isPromotion` filter**
(`:5928`); the Promotion table filters `e.isPromotion` (`:7762`). Counted
mounted at the same moment: **Volume 1, Promotion 1**.

**The asymmetry is inside the Volume card**, not between the cards: its
**campaign** grouping *is* filtered
(`groupByCampaign(marketEvents.filter(e => !e.isPromotion))`, `:3672`). The
campaign path already treats promotions as not its own; the row path does not.

### The options — for Jon, not chosen here

1. **The Volume pencil routes promo-built rows to the Promotion card.** One
   editor per event shape; the row stays visible where a user expects to see
   every event.
2. **Promo-built rows are read-only in the Volume table** — no pencil, matching
   what the campaign grouping already does.
3. **Leave it, with the arms preserved on save.** Nearly the present state, but
   it would need the **rate** preserved too, since today it is zeroed.

Recorded in `EXPECTED.md` with the measurements. The mounted check pins
**today's** behaviour as *measured, not endorsed*: exactly two fields move and
one is the baked rate. Whichever option lands, that check must change — and its
failing is the signal that the decision arrived.

## Limits of this check

- **D5-04 is measured on ONE promotion shape** — percentage, Retention, value
  mix, one lock, no pricing arm. A promotion carrying a dilution arm or a
  spread is reasoned from the patch's field list, not driven.
- **The pinned D5-04 check encodes a defect.** It is labelled as such in the
  spec and in EXPECTED.md, but a reader who sees only a green gate would not
  know the promotion's rate is being zeroed. That is the cost of measure-only,
  and it is why the option list exists.
- **D5-03's campaign path is not driven mounted.** The restore is symmetric
  with the single-row path and reads `first`, but only the single-row path is
  exercised through the card.
- **The dependency-array fix is not trapped.** Adding four names to three
  arrays is guarded by nothing; a future removal would be caught only if it
  changed behaviour on a driven path.
- **No walk, no browser.** Everything is the mounted card on constructed
  fixtures.
