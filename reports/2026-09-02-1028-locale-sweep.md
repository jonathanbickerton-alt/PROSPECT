## Item 1 — the scan, and the premise it corrected

### The true flagged count, measured before any work

The brief inherited the 1924 report's figure — *50 of 76 guide-quoted keys
identical to English*. That number is accurate about the 76 keys the guide
quotes and badly misleading about the application, because those 76 were a
**sample of what the guide happened to mention**, not a census.

The census:

| Locale | Keys | Translated | **Identical to English** | Missing |
|---|---|---|---|---|
| de | 822 | 119 | **703** | 9 |
| es | 822 | 122 | **700** | 9 |
| fr | 822 | 118 | **704** | 9 |
| it | 822 | 119 | **703** | 9 |

**The app was about 14% translated.** What had been done was the Home tab, the
step indicator and the upload screen — the first thing anyone sees, which is
also why the gap survived: every casual look at the German build landed on the
translated part.

### Nothing measured this, and the tool that should have says why in its own comments

`scripts/scan-i18n.ts` carries a block headed `LOCALE PARITY`. It asks only
whether the key **exists**:

```ts
const missingFrom = LOCALES.filter(l => !(key in others[l]));
```

Twelve lines below, the staleness check carries this:

> `PRESENCE IS NOT TRANSLATION. This tested only that the key existed in each`
> `locale, so a key carrying identical ENGLISH in all six read as "translated`
> `everywhere"… A locale now counts as translated only if its value DIFFERS`
> `from the English one.`

That is exactly the defect, correctly diagnosed, **fixed for itself and left
standing in the check above it** — in the same block, under the comment
explaining why it is wrong. So the class was invisible to the tool named for it,
and the scan reported clean over 703 English strings.

### The spec

`scripts/i18n-parity-spec.ts`, wired as `npm run spec:i18n-parity`. It asserts:

1. every English key exists in all five locales (absence renders English by
   `fallbackLng`, which is the same user-visible defect by another mechanism);
2. **zero** non-allowlisted keys carrying the English string, per locale;
3. the allowlist is **exactly 52 entries and exactly 184 (key, locale) pairs**;
4. **no stale exemption** — an entry whose key no longer equals English fails,
   so the list cannot quietly grow into a blanket;
5. the hardcoded literals are gone and their keys are used (item 3);
6. no Step-3 band line falls back to its dataKey (item 4).

**Exact counts, not floors.** Trap 77 established in August that a floor stops
discriminating the moment anything is added. An allowlist is the structure where
that would be most dangerous, because the cheapest way to make a parity failure
disappear is to allowlist the key. Both counts are pinned, and the negative
control below shows the pair count catching drift the per-locale check also
caught — two independent routes to red.

## The allowlist — 52 entries, each with a reason

Scoped per locale, because the same English word translates in some locales and
not others. Grouped by why:

| Group | Entries | Basis |
|---|---|---|
| Language endonyms | 6 | the picker names each language in itself |
| TERMBASE §1 never-translate | 13 | ARPU, MAPE, SES, the IBRO scenario names and compounds built only from them, the Base(t) formula, the PROSPECT backronym |
| TERMBASE §6 Mix | 3 | Mix is Mix in all six |
| Feature names | 2 | `Yield`, `Pricing` |
| Placeholders / markup | 4 | `{{scenario}} {{amount}}`, `&rdquo;`, `en-US`, `%` |
| Words that genuinely coincide | 24 | Volume (fr/it/pt), Segment (de/fr/pt), Scenario (it), Promotion (de/fr), Dashboard (de/it), Band/Status/Trend/Name (de), Actions/Date/Mode/Direct/Dilution (fr), (optional) (de/it), Home (it) |

**The two feature names were verified, not assumed.** The brief asked for that
test on the four scenario names; TERMBASE §1 settles those by business ruling.
`Yield` and `Pricing` are not on §1, so I checked the translated guide instead:
the German block uses **Yield 16 times with zero German alternatives**
(no *Ertrag*, no *Rendite*), and uses *Pricing* attributively — *"die
Pricing-Karte"*, *"die Pricing-Ziele"*. Both are established app vocabulary in
the locale. Marcel can overrule either in UAT; that is what native review is
for, and the entries are one-line edits.

### The allowlist is load-bearing, not bookkeeping

Without it, a strict parity check **pressures you to invent a difference**. I
did exactly that and caught it: for Italian `baseline_volume` I wrote *"Volume
dei dati"* — where the Italian for "Volume" is simply "Volume" — purely so the
value would differ. That is the check making the UI worse.

It happened three times in all (Italian `baseline_volume`, French
`common_segment`, and a French `Segment client` for a bare "Segment"), each
caught by the merge tool refusing a value identical to English and me then
asking *why* rather than reaching for a synonym. Each reverted to the English
form and allowlisted with a reason.

**That is why Jon's recorded decision requires a justification per entry rather
than just a list.** A bare list of exemptions and a list of reasons look the
same in a diff and behave completely differently under pressure.

## Item 4 — UAT-D2-01, the Step 3 tooltip

**The defect is larger than the brief describes.** The brief reports raw field
names (`inflowArpu_opt` / `_pess`) leaking into the tooltip. The cause is that
the band lines carried **no `name` prop at all**, so Recharts fell back to the
`dataKey` and the tooltip formatter passed it through verbatim:

```tsx
<Line dataKey={`${prefix}_opt`}  … legendType="none" … />   // no name → "inflowArpu_opt"
<Line dataKey={`${prefix}_pess`} … legendType="none" … />
```

`legendType="none"` hides them from the legend but **not** from the tooltip,
which is why this survived: the series is invisible everywhere a reviewer would
think to look, and visible in the one place nobody scrolls to.

**And the two lines that did carry a name carried English:**

```tsx
name={`${scenarioLabel(sc)} Forecast`}     // hardcoded, on both branches
name={`${scenarioLabel(sc)} Actual`}
```

So the tooltip was showing *two* raw field names and *two* untranslated words.
All four now come from the locale — `actuals_series_optimistic`,
`_pessimistic`, `_forecast`, `_actual` — across both the volume and value
branches, eight sites in all. The spec asserts each key appears exactly twice
and that no `_opt`/`_pess` line lacks a `name`.

## Limits of this check

**Parity is not quality, and this report does not claim otherwise.** What is
proven is that a translated string exists, differs from English, follows the
termbase, and holds a formal register. Whether it reads the way a native
speaker would have written it is **Marcel's (de) and Alessandro's (it) call in
UAT** — that is the stated follow-up, and nothing here substitutes for it. The
Romance locales have no named reviewer.

**THE TRANSLATED USER GUIDE NOW CONTRADICTS THE APP, and this session did not
fix it.** Each of the five translated guide blocks carries an aside that reads,
in German:

> *"Teile der Anwendung sind noch nicht übersetzt. Bedienelemente, deren
> Beschriftung in dieser Anleitung englisch wiedergegeben ist — die Namen der
> Registerkarten, die Spread-Elemente, die Pricing-Ziele, die Schaltflächen zum
> Speichern und Laden —, erscheinen auch in der deutschen Oberfläche englisch."*

Every named example except *Pricing* is now translated. The note was describing
**debt** — *"noch nicht übersetzt"* — not a design decision, which is what
settled the tab-name question in this session's favour; but it also means the
note is now wrong in the direction that tells a German reader to expect English
where they will see German. It is out of this brief's scope (src/ and Step 3),
it touches five translated blocks that two prior sessions ruled must not be
edited casually, and the correct rewrite depends on this session's final
residue. **It needs its own short docs pass.**

AND LISTED HERE.** `scan-i18n` already buckets them as `7 ts-utility (MUST
KEY)` — its own label for "this should not be here" — and it exits 0 anyway,
so they have been tolerated rather than tracked:

These are the mix card's refusal reasons — genuinely user-facing. They are
**not fixed here** for three reasons, all of which should be weighed rather
than assumed: they are one coherent module rather than scattered strays, so
they make a clean unit of work; every one interpolates, several twice, so
translating them well means checking German and Italian word order rather than
substituting; and none was reached by this session's walk, so fixing them
blind would produce translations nothing had rendered. They are pre-existing
debt this session surfaced, not debt it created.

**The one bucket-6 hit is not copy.** `compare-events-{}` at
`ScenarioCompareTab.tsx:685` is a key/testid, and the scanner flags it only
because it looks like an interpolated string.

**String concatenation makes some sentences ungrammatical in translation, and
translating the fragments cannot fix that.** Keys like `bulk_don_t` ("don't"),
`whatif_retention_volume` ("Retention volume (") and
`actuals_challenger_performs_better_on_historical_data` are **sentence
fragments assembled at render time**. English word order is baked into the
assembly, so German and Italian versions of the fragments still produce
awkward — occasionally wrong — sentences. I translated each fragment as well as
it can be translated in isolation and did not restructure the call sites, which
would be a `<Trans>` conversion and a separate piece of work. TERMBASE §12
already tracks a deferred `<Trans>` backlog; this belongs with it.

**Layout was not measured.** TERMBASE §10 warns that German and French run
longer and that the Over/Under column is narrow. I kept the short labels short
(*↑ Über* / *↓ Unter*, *Abw. %*, *Vor-Unsich.:*) but did not measure any column
at a real viewport, so overflow in a dense table is possible and unproven either
way.

**The render check is a smoke test, not a sweep.** It confirms the named screens
draw in de and it with no English on them and no console errors. It does not
visit every dialog, every empty state, or every error path — several of which
need data conditions the fixture does not produce.
