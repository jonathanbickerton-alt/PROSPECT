### (b) Cohorts + Base — it double counts, and it compounds

Measured through the **real `scenarioAdjustedArpu`**, the function the base
scenario is built from, with a pool carrying the already-priced rate and the
same event handed in as `pricing`:

| case | Base ARPU at T+1 | revenue |
|---|---|---|
| today, Cohorts only | 14.5100 | 14 133 |
| PROPOSED, Cohorts only | 14.7930 | 14 408 |
| PROPOSED, Cohorts + Base **One-Off** | 14.7930 | 14 408 |
| PROPOSED, Cohorts + Base **Recurring** | **15.7793** | **15 369** |
| today, Cohorts + Base Recurring | 15.4773 | 15 075 |
| PROPOSED with `pricesPools: false` | 15.4773 | 15 075 |

**+0.3019 ARPU and +294 revenue at T+1, compounding every later month.**

The mechanism is `scenarioArpu.ts:144-152`:

```ts
for (const p of input.pricing ?? []) {
  if (p.pricesPools || poolVol <= 0) {
    arpu = applyDelta(arpu, p);          // the WHOLE blend, pools included
```

`pricesPools` is `pe.target !== 'base-only'` (`WhatIfTab.tsx:1886`), so a
**cohorts+base** event prices the whole blend — and under the decision that
blend now contains a pool already carrying the priced rate. **One-Off escapes**,
because at T+1 the event no longer applies and `pricingFor('base')` returns
nothing.

Per the brief this is a decision, so the interaction is reported and not
resolved. Worth stating plainly: the obvious repair — pass `pricesPools: false`
once a cohorts+base event carves a pool — reproduces today's figure **exactly**
(15.4773 / 15 075). That is either the right answer or a coincidence, and which
it is should be decided rather than inferred from the match.

## 2. Build — not started, and why

**STOP: the decay term has no source.** The decision says the pool decays "by
contract length". A `PricingEvent` (`types/forecast.ts:395-420`) carries
`month`, `inputMode`, `amount`, `target`, `cohortScope`, `duration` and the
dilution pair. **There is no `contractLength`.** It lives on `MarketEvent`
(`forecasting.ts:101`, exported as `Contract_Length_Months` at `:347`) because
the Promotion card asks the user for it; the Pricing card never does.

`DEFAULT_CONTRACT_N = 24` exists in both engines (`WhatIfTab.tsx:1334`,
`scenarioHelper.ts:310`) and reaching for it would compile and would look
right. It would also **invent the pool's entire persistence profile** from a
constant the user never stated — and the persistence profile *is* the change
Alessandro asked for. The brief reserved this ("if a pricing event has none,
STOP and report — the decay term is a decision"), so it is reserved.

**The options are recorded in D5-14**: a new field with card, column and reader;
`DEFAULT_CONTRACT_N` as a stated rule rather than a silent fallback; or no decay
at all, the pool persisting until base churn takes it.

**This blocks the Cohorts-only case too**, so it was not built either: a pool
with no stated decay is not the pool D5-14 describes. Items 3, 4 and the pool
sites are therefore not reached.

**The pool arithmetic is still ONE.** For the record, the grep the brief asked
for, taken now rather than after a build: `p_eventPools.push(` appears **three**
times in `WhatIfTab.tsx` (`:1492` Inflow, `:1556` Inflow at the lag, `:1612`
re-banded Retention) and **once** in `scenarioHelper.ts` (`:400`). Those are the
existing sites; **no second construction was added, because nothing was added.**
