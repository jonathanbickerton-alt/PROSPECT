## Item 1 — the measurement

### The brief's premise does not hold, and that changed the method

The brief asks for `git diff --stat main...ai-capability` in both directions.
That diff is **empty**, and not because nothing differs:

```
git merge-base main ai-capability   →  b2d5a5e...  (= the ai-capability tip)
git merge-base --is-ancestor ai-capability main  →  YES
git rev-list --count main..ai-capability  →  0
git rev-list --count ai-capability..main  →  626
```

`ai-capability` is an **ancestor** of main — its tip *is* the merge base. It has
zero commits main does not have and sits 626 behind. `main...ai-capability`
(three-dot) therefore compares the merge base against itself and returns
nothing, which reads as "the branch adds nothing" and would have been a false
all-clear had I stopped there.

This is consistent with what EXPECTED.md §33 already records — *"the
`ai-capability` branch on origin, and the AI capability reachable in main's
history, are a deliberate preservation"* — but it means the branch is a **frozen
snapshot of the pre-removal tree**, not a divergent line of work. So the
measurement had to be done two other ways: compare the two **trees**, and read
the **removal commit**.

### The leak check

**Against the hold's own definition — EXPECTED.md §33 "AI capability — hard
gate" — all three criteria are clean:**

| §33 criterion | result |
|---|---|
| No AI/LLM SDK dependencies in `package.json` | **clean** — `@google/genai` absent from `package.json` and `package-lock.json` (0 occurrences) |
| No AI/LLM imports, model API calls or API-key patterns in `src/` | **clean** — zero occurrences across all `.ts`/`.tsx` |
| `.env` not tracked by git (only `.env.example`) | **clean** — `git ls-files \| grep -i env` returns `.env.example` only |

**Against the brief's broader tripwire — "if ANY identifier is present on main,
STOP" — two hits:**

**Hit 1 — `APP_URL`, in main's tracked `.env.example`.** Present, with its
AI-Studio comment intact:

```
# APP_URL: The URL where this applet is hosted.
# AI Studio automatically injects this at runtime with the Cloud Run service URL.
APP_URL="MY_APP_URL"
```

**Hit 2 — `GEMINI_API_KEY`, in two gitignored local directories.**
`_archive/v4.3-extracted/.env.example` and
`.claude/worktrees/intelligent-ellis-5eeaf2/…/.env.example` both carry the full
pre-removal file including `GEMINI_API_KEY="MY_GEMINI_API_KEY"`. Both paths are
gitignored (`.gitignore:12 /_archive/`, `.gitignore:34 .claude/worktrees/`), so
neither is tracked, neither can be pushed, and neither is built — Vite builds
from `src/` and `index.html`. `git grep` over tracked files returns **zero**
files containing any of the three AI identifiers. The value is the template
placeholder, not a real key.

### What the mechanism says, and why that is a finding rather than a licence

`git log -S "GEMINI_API_KEY" --follow -- .env.example` returns exactly one
removal: **`432837d`, 2026-06-18, "Remove AI capability from main ahead of prod
deployment pending approval"**. That commit takes 5 lines out of `.env.example`
— the `GEMINI_API_KEY` block — and **keeps `APP_URL`**.

So `APP_URL`'s survival is not drift. It was retained, deliberately, in the same
commit that removed the AI capability, by the person who removed it. On my
reading that settles it: `APP_URL` is a deployment URL, not an AI capability,
and it is on main on purpose.

**I am reporting it rather than acting on it.** The brief said a hit means Jon
decides before anything is built, and CLAUDE.md's reserved-decisions rule says a
reserved decision stays reserved "even where the answer looks self-evident" —
the evidence being overwhelming is explicitly not an exception. This project
also has a standing rule that a mechanism which exonerates the suspect is a
finding, not a licence to build. All three point the same way, so I stopped.

## What I need from Jon before Item 2 can be built

**Q1. Is `APP_URL` in scope for `spec:ai-hold`?** If yes, the spec would go red
on main today and the first thing it does is fail — so `APP_URL` would have to
come out of `.env.example` first, which is a product change (it may be load-
bearing for a Cloud Run deploy) and not mine to make. If no, the spec pins the
three AI identifiers only, and I would note in the spec why `APP_URL` is
excluded, citing `432837d`.

**Q2. Should the spec cover gitignored working-tree paths, or tracked files
only?** These give different answers today: tracked-only is green, working-tree
is red because of `_archive/` and the agent worktree. §33's own scope sentence
says the check "verifies the *working tree*, and therefore what is actually
built and deployed" — but `_archive/` is neither built nor deployed, so the
sentence's two halves come apart here. My recommendation, for what it is worth:
assert over **tracked files**, and add a separate advisory line for gitignored
hits, so a stale local archive cannot fail a gate that is meant to guard what
ships. But this is the reserved half of the question and I have not acted on it.

**Q3. Given there is no call site even on the branch, should the spec assert
absence of the four identifiers, or absence of the seven paths, or both?** Four
of the seven paths are the Streamlit prototype and have nothing to do with the
hold; pinning them under an AI-hold spec would mislead a future reader about
why they must stay absent.
