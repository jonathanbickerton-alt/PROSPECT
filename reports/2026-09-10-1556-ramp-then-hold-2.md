## 1. The churn held tail

One derivation, feeding the fold's one input:

```ts
const churnStatedWithHold: number[] = useMemo(() => {
  const ramp = churnRampOn ? churnStated.slice(0, churnMonths) : [churnTargetPct];
  if (!churnHold) return ramp;
  const reached = ramp[ramp.length - 1] ?? 0;
  const span = horizonMonthsFrom(newEvent.date ?? '');
  const tail = Math.max(0, span - ramp.length);
  return [...ramp, ...Array.from({ length: tail }, () => reached)];
}, [...]);
```

**`churnFold.ts` was not touched at all.** The fold already iterates
`statedReductions.length` and already clips with `if (!m) break`, so a
trajectory longer than the scoped series is safe by construction rather than by
a length check I would have had to add and keep correct.

**`horizonMonthsFrom` is the volume path's function**, moved earlier in the
component so both consumers can see it — not copied. It was declared after the
churn memo and a second copy would have been two things to keep in step.

Separated from the fold memo because the grid, the Add handler **and the button
count** all need the trajectory, and deriving it three times is how three
readings come to disagree.

**The Add button, and the one place I overreached — see §7.** It read
`spreadEnabled ? spreadMonths : 1`, and `spreadEnabled` is force-cleared for
churn, so it has said *"Add Event"* for a three-month ramp since R7 and would
now have said it while adding twenty-three. **Only the held case is fixed**:
under hold it reports the fold's own usable count (`!absence && delta !== 0`),
which is exactly what the handler emits, and the unheld label is byte-identical
to what it was. Correcting the pre-existing case as well is what broke the gate.

## 2. Not compounding — and where the brief's tolerance does not hold

The fold computes `target_i = current_i − stated_i` with `current_i` read from
the **unadjusted** series each month. A repeated `2` therefore asks every held
month to sit two points below its own untouched rate. The plausible wrong
version derives each held month from the previous **adjusted** rate — 2, 4, 6,
8 — and churn walks to zero on a curve that is reasonable month by month. That
is trap 207.

### The measurement, and the miss

The brief asked for adjusted ÷ baseline outflow **equal within 0.5%** at
campaign months 3, 6, 12 and 20. Measured on the fixture:

| campaign month | forecast index | ratio |
|---|---|---|
| 3 | 3 | 0.908873 |
| 6 | 6 | 0.910610 |
| 12 | 12 | 0.913840 |
| 20 | 20 | 0.917711 |

**Worst spread 0.9724%.** The brief's 0.5% is not met, and I have not widened
it quietly.

**It is not a defect, and the direction is the proof.** The ratio **rises**. A
compounding tail **falls** — trap 207 measured it falling to 0.909 / 0.641 /
0.086 / 0.000. What this is, is decision 2's own arithmetic:
`ratio = 1 − stated / current`, and `current` drifts as the forecast trends and
as the base grows under the campaign's own effect. Two points off 21.1% and two
points off 21.5% are different proportions of a different number. Nothing makes
them equal except holding a **proportion** instead of points — which is a
different decision from the one recorded.

**What I did instead**, on the D5-15 precedent where Compare's "to the penny"
parity was unmeetable and became a measured, pinned tolerance:

- the **decision itself** is asserted directly — every held month's row states
  the same 2 points, which is what *"2% reached is 2% held, never compounding"*
  actually claims and which no fixture coincidence can satisfy;
- the ratio band is **pinned at 1.0%** with the measured 0.9724% recorded in
  the spec beside it;
- a separate check asserts the ratio **rises rather than falls**, so the two
  failure modes read differently.

**This is Jon's call, not mine**: accept the 1.0% band, or re-specify hold as a
held proportion rather than held points. I have changed nothing in the recorded
decision.

## 7. The gate refused to run, and it was right

**The first guard-traps run produced no trap results at all:**

```

[INCONCLUSIVE] control. The spec is RED on the unmutated tree.
               Every trap would catch vacuously. Fix the spec first.
```

That is the harness's **positive control**, working exactly as designed and
costing a full run rather than reporting 204/204 against a spec that was already
failing.

**The red spec was `spec:mix-card`, and I caused it.** I had corrected the churn
Add button's label — a pre-existing inaccuracy, not this session's brief — and
`spec:mix-card` finds that button by the literal text `"Add Event"`:

```ts
.find((b: any) => (b.textContent || '').trim().startsWith('Add Event'));
```

The label became *"Add 3 Events"*, the click stopped landing, and **eleven churn
checks went red on a button that was never pressed** — every one of them
reporting `0 added` while the derived column beside it showed three real deltas.

**This was unbriefed scope and it should not have been taken.** The fix is now
narrow: the unheld label is frozen byte-identical, only the held case reports
its count, and both the code and `spec:churn-hold-mounted` case 2 now pin the
frozen label so a future session tidying it sees why it must not.
`spec:mix-card` is back to **237/237**.

### The gap the failure exposed

The control list did **not** include `HOLDSHAPE`. Session 1 registered four
traps (202–205) against that spec and never added it to the control — so a red
hold-shape spec would have let all four "catch" vacuously, which is the precise
failure this control exists to prevent. **Both `HOLDSHAPE` and `CHURNHOLD` are
in it now**, with the reason recorded at the line.

The re-run against the corrected tree is the **204/204** in the gate table, and
it re-verified 202–208 against the committed tree — which is the check that
counts, and supersedes the hand-plant note in §5.

  session 1 but was not re-verified by a Compare run.
