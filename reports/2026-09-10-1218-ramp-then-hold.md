## 1. The Hold-ON generator

`spreadShape` in `WhatIfTab.tsx`, exported beside `buildPromoEvents` — where
the spread arithmetic already lives, and where specs already import from.

```ts
export function spreadShape(input: SpreadShapeInput): SpreadShapeMonth[] {
  const months = Math.max(1, Math.floor(input.months) || 1);
  const pcts = input.dist.slice(0, months);
  const total = pcts.reduce((s, p) => s + p, 0);
  if (!(total > 0)) return [];
  const out: SpreadShapeMonth[] = [];
  if (!input.hold) {
    for (let i = 0; i < months; i++) {
      out.push({ offset: i, fraction: pcts[i] / total, held: false });
    }
    return out;
  }
  let cum = 0;
  for (let i = 0; i < months; i++) {
    cum += pcts[i];
    out.push({ offset: i, fraction: i === months - 1 ? 1 : cum / total, held: false });
  }
  const span = Math.max(months, Math.floor(input.horizonMonths) || 0);
  for (let i = months; i < span; i++) out.push({ offset: i, fraction: 1, held: true });
  return out;
}
```

It returns a **fraction per month**, not a volume, because the callers scale
three quantities by it — subscribers, customers and revenue — exactly as the
hand-rolled arithmetic did.

**The last ramp month is a literal `1`, not `cum / total`.** Three additions of
`100/3` reach `100.00000000000001`, and the user would have seen 2,499 where
they typed 2,500. This is the same property `churn-fold-spec.ts:244` already
pins on the churn carrier — *"the last month always equals the target"* —
asserted here with `===` rather than a tolerance.

**Four call sites, one shape**: the add path, the campaign rebuild, the
preview table, and the Add button's own row count.

### The horizon

```ts
const horizonMonthsFrom = useCallback((startMonth: string): number => {
  const idx = adjustedMonths.findIndex(m => m.month === startMonth);
  return idx < 0 ? 0 : adjustedMonths.length - idx;
}, [adjustedMonths]);
```

`adjustedMonths` is the array `deltaMonthOptions` maps — reused, not
re-derived, as the brief required. The selector then filters months carrying
actuals; this does not, because a month with an actual is still a month the
campaign occupies. A start month outside the horizon returns **0**, which
`spreadShape` reads as "no months to hold into" and emits the ramp alone
rather than inventing a tail.

## 3. Edit-restore

A held campaign's rows **sum to far more than the target**, so the existing
reverse-engineering would have seeded the amount box with a number the user
never typed and a forty-month ramp. `handleEditCampaignStart` therefore branches
on `rows.some(e => e.hold)` before that arithmetic runs, and restores decision
5's three values: the **toggle from the column**, the **target from the last
row**, the **ramp length from the plateau start**.

```ts
export function holdPlateauStart(figures: readonly number[]): number {
  if (!figures.length) return 1;
  const last = figures[figures.length - 1];
  const tol = Math.abs(last) * 1e-9 + 1e-9;
  for (let i = 0; i < figures.length; i++) {
    if (Math.abs(figures[i] - last) <= tol) return i + 1;
  }
  return figures.length;
}
```

**The tolerance is relative, and that is load-bearing.** My first draft used
half a subscriber. It reads fine on volumes and destroys a percentage ramp: a
held +0.4% campaign stores 0.13 / 0.27 / 0.40, every step is inside half a unit
of the target, and a 0.5 tolerance calls **month 1** the plateau. The spec pins
that case by name.

**The toggle is set unconditionally on every restore path** — the single-event
pencil, the held branch, the plain-spread branch and the churn branch — because
the card is a long-lived form and a one-sided restore leaves a draft carrying a
control the user never touched. Here that would silently re-materialise a tail
on the next save.

## 4. The Hold-OFF differential

Decision 3 promises byte-identical on a path this session rewrote, so asserting
the new code against itself would prove nothing. `spec:hold-shape` section 1
pins it against **six hand-written literals**, each computed from the c11151e
arithmetic and annotated with the division that produces it:

| draft | expected, hand-computed | why |
|---|---|---|
| 300 over 3 even | `100,100,100` | `300 × 0.3333333333333333 = 99.99999999999999` |
| **2500 over 3 even** | **`833,833,833`** | the split — decision 2's same figure is `833,1667,2500` |
| 100 over 3 even | `33,33,33` | loses 1 to rounding; preserved, not repaired |
| 2500 over 4 even | `625,625,625,625` | `100/4 = 25` exactly |
| custom 50/30/20 of 1000 | `500,300,200` | |
| shares `[1,1,1]` of 10 | `3,3,3` | normalised, not assumed to sum to 100 |

Every case passes `horizonMonths: 60` deliberately: with hold off it must have
no effect at all, so a leak would fail on the **row count** before any figure.

## 7. Where I settled a question rather than working around it

Mounted case (a) requires a **percentage** draft with a 3-month ramp. The card
hides the spread control for percentage drafts, with a recorded reason:

> *"spreading a percentage is ambiguous (is 10% over three months a total of
> 10%, or 10% in each month?) and no answer to that was settled."*

**Decision 2 is that answer.** Under hold it is neither of the two the comment
names: 10% over three months is 10% *reached* at month three and held. That
reading exists only because the entered figure became a TARGET, which is
exactly what the old ambiguity lacked.

So the section opens for a percentage draft **only once hold is on**. With hold
off it stays hidden and byte-identical, and the unsettled question stays
unsettled where it still applies.

That forced a second change: `Math.round` on the amount. It is right for
subscribers and destroys a percentage ramp — 3.33 / 6.67 / 10 becomes 3 / 7 /
10, where the only month the user would recognise is the last. Percentage
amounts are no longer rounded; absolute ones round exactly as before, which is
what decision 3's byte-identity is a claim about.

**I am flagging this rather than burying it**: it is a capability the brief's
own never-shed case requires and the six recorded clauses do not spell out.

## Limits

- **Percentage spreads are new capability**, and section 7 says so rather than
  letting it pass as a Hold toggle. If that reading of decision 2 is wrong, the
  revert is small: restore `!isPercentageDraft` on the section guard and the
  unconditional `Math.round`.
- **The held tail is bounded by the horizon at BUILD time.** Regenerating the
  base forecast over a longer horizon does not lengthen an existing held
  campaign's rows — decision 1 materialises rows, so a campaign is as long as
  the forecast it was built against. Not a defect, but not stated in the six
  clauses either.
- **Case (b)'s 6,600 is this fixture's arithmetic**, not a general identity: it
  holds because the event is a linked Retention event on a 24-month horizon
  starting at month 1.
- **Nothing was run against a browser.** No UI was exercised by hand; the card
  was driven only through JSDOM.
- **Compare was not re-measured.** The claim that it needs nothing rests on the
  tail being ordinary rows, which the round-trip case asserts, not on a Compare
  run.
- **The `Add N Events` label is now derived from the generator**, so it changed
  for the no-hold spread too — from `spreadMonths` to the emitted count. Those
  are the same number with hold off, asserted in case (c).
