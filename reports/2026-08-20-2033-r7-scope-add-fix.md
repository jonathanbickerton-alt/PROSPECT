## 1. Fix B — the routing

The churn branch now runs **before** both early returns in
`handleAddMarketEvent`. That is the whole change, and the diagnosis had already
named it exactly.

It was dead code because churn **force-clears `spreadEnabled`** — correct, since
churn replaces the spread with its own ramp radio — and `spreadEnabled` is
**also** the gate routing to the N-events emitter. One flag, two jobs. Every
churn Add fell to App's `addMarketEvent`, the writer its own comment calls the
**fifth writer**, which emitted one event from the amount field churn had just
zeroed and knew none of the four churn fields.

**Placing it above both returns is not defensive ordering.** It is the statement
that a churn draft is not a spread question at all. The mount pins the ordering,
because a routing fact that lives only in line numbers is one refactor from being
dead again — and **trap 102 plants exactly that refactor**.

The `App.tsx:221` `neg` hazard needs no code change: a churn delta can no longer
reach that writer, and the mount's *"App's fifth writer is never reached by a
churn add"* assertion is what proves the unreachability rather than asserting it.

## 2. Fix A — the feed

```ts
const churnScopeResolution = useMemo(() => {
  if (!isChurnDraft) return null;
  const key = makeForecastKey(segment, product, productL2, channel, channelL2, tariffL1, tariffL2);
  return resolveForecast(key);
}, [...]);
```

and the series memo feeds `churnScopeResolution.forecast` instead of
`baseForecast`.

**The diagnosis was right that nothing made this unreachable**: `resolveForecast`
is on the context, `useForecast()` was already destructured, and no new machinery
was needed. Two properties came free, as predicted — aggregates **derive** rather
than needing to be stored, and a slice with no forecast returns a **reason**.

**The seam's reason reaches the user verbatim.** A null resolution renders
*"No baseline forecast covers this cohort (never-enumerated), so there is no
churn rate to reduce."* Substituting a generic sentence would have been the
two-meanings-of-null defect at a third site. That message proved its worth during
the build: it named `never-enumerated` and told me my own fixture had lost the
segment.

**The seed gate moved with the feed.** `canShowBaseForecast` now reads the
**scoped** forecast: a slice can be seed-unknown while the aggregate is not, and
the absence must belong to the slice the user is stating a rate for.

## 3. The hides

The four companions — Customer Volume, Revenue, ARPU, Contract Length — and the
volume spread control do not render on a churn row.

**They are inert**: `applyEventsToMonth` reads `subscriberVolume` alone on this
path. **Revenue would be worse than inert** — the money from subscribers who did
not leave is already carried by the base × ARPU recursion, so the field would
state it twice.

**An editable field the engine ignores is the silent-handling defect as an
input.** This codebase has applied that principle three times to outputs that
could not speak; this is the same rule pointed at a control that accepts a number
and does nothing with it.

**Keyed on the one derived control**, never a second flag — the
two-sources-of-truth root cause is one session old, and reintroducing it through
the fix for its own symptom would be a poor trade. Trap 104 plants it.

## 4. The mount — and what it caught immediately

Extended into `spec:mix-card` rather than given its own file, per the recovery
report's Finding D: *two harnesses for one card drift*. **99 → 127 checks.**

**What is driven**: the real `WhatIfTab`, the real churn panel, the real fold,
the real `amountControl` writer, the real Add handler, and a real
`ForecastProvider` whose store holds **two leaves plus a leafMap**, so the
unscoped draft *derives* from both and the product-scoped draft from one.
**What is stubbed**: the draft dims are set through `setNewEvent`, which is
exactly how the real dropdowns set them; and `addMarketEvent` is a **spy**,
because the assertion that matters is that a churn add never reaches it.

### It found two defects on its first run

**(i) The harness crashed: `resolveForecast is not a function`.** It is a
**required prop** on `ForecastProvider` that this harness has never passed —
`ForecastProvider as any` hid it from `tsc` for as long as the harness has
existed, and no consumer had called it until fix A. Both providers now supply the
real seam over their own stores.

**(ii) A real production defect: a stale `churnFold`.** `handleAddMarketEvent`
**reads** `churnFold` but did not **depend** on it, so it held the fold as it
stood before the last change. Turning the ramp on and clicking Add emitted the
**pre-toggle** fold — one month instead of three.

That is the **hook dependency-array read-set** rule this codebase already has a
recorded lesson about, and it is precisely the class the pure specs cannot see:
`spec:churn-fold` proves the fold's arithmetic and `spec:amount-control` proves
the transitions, and neither can observe what a *handler* was holding when it
ran. The read-set is now closed and stated in a comment at the site.

### Two fixture findings, reported not repaired

**The harness's `C.prod` is `'Product_Category'`, which does not exist in its own
fixture** — the column is `Product_L1`. It has therefore always fed `WhatIfTab`
an **empty product tree**. The promotion section never depended on it and never
noticed. Not repaired here: changing it would move the existing checks' inputs,
which is not this session's business.

**The fixture carries `Customer_Volume` and `Avg_Subscribers_per_Customer`** as
raw columns. That does not contradict the diagnosis — which found no customer
series in any *forecast* — but it sharpens decision 4: the ratio exists **in the
upload** and is dropped by the pipeline, so building it would be plumbing an
existing column through rather than inventing data.

### CORRECTION, appended 2026-08-21 — the conclusion above is refuted

**Appended, not rewritten**, so the error and its correction both stay readable.

This section concluded that the exposure was **partial**: `pricedVol` scoped and
right, only `totalVol`'s base term cohort-scoped. **That is wrong.** Report
`2026-08-20-2233-pricing-totalvol-scope.md` reconstructed the slice's own base
and measured **both** stored figures as the LOADED COHORT's, to the penny —

8,486.48. The 1.8% agreement above is a coincidence between two wrong
quantities: the event is a **dilution**, so `cohortScope` is `'retention'` and
`pricedVol` is retention alone, but it was compared against the slice's

## Limits of this check

**The mount is jsdom, not a browser.** Layout, real event ordering and CSS are
not exercised; what it proves is that the component's state, handlers and
conditional rendering behave as claimed when driven through the real props.

**Dims are set through `setNewEvent`, not through the dropdowns.** That is how
the real dropdowns set them, but the dropdowns themselves are not clicked — so a
defect in a dim control would not be caught here.

**The pricing finding is one event on two saves**, and one of the two is a copy
of the other. It is a measurement, not a survey, and the base-scope conclusion is
an inference from the residual rather than a reconstruction of the slice's base.

**Fix A is not proven against a real save.** The mount's store is constructed;
no saved session was loaded and re-scoped. What the walk showed as ~293k at every
slice is now shown to change with the dims **in the harness**.
