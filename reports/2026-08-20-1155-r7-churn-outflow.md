## 1. The carrier

Four fields on `StoredEventModifiers`, and therefore on `MarketEvent`:
`churnMode?: 'churn'`, `churnTargetPct`, `churnCurrentPct`, `churnPrevBase`.

**They ride `readStoredEventModifiers`**, so both market import routes inherit
them from one place and the exactly-one-spread pin stays true. That is the
lesson the promo fields paid for: a field hand-rolled per route reaches one
route.

**`''` is the absence carrier on all four columns**, through the existing
`readOptionalNumber`. A stated reduction of **zero points is a real statement**
— "no reduction this month" — and must not read as unset. Asserted both ways.

**`churnMode` is presence-as-carrier**: there is no 'plain' value to confuse
with an unset one.

The writer gains four columns and the eleven-column enumeration in
`spec:event-roundtrip` grows to fifteen — an enumeration rather than a count,
precisely so a dropped column is visible.

### Churn is not a value of `amountType`

The obvious implementation is a third `amountType`. It is wrong, and the spec
asserts against it: **`amountType` is read by the engine**, so putting `'churn'`
there would make churn an engine behaviour — exactly what decision 1 says it is
not. A stored churn row is `amountType: 'absolute'` **plus** `churnMode: 'churn'`:
an ordinary absolute outflow row that remembers how it was stated.

The lit arm is therefore **draft-local component state**, not a draft field.

## 2. The fold

`foldChurnRamp` in `src/utils/churnFold.ts` — pure, dependency-free, no React.

The arithmetic collapses to an identity worth stating, because it makes every
figure checkable in one step:

```
target    = current - stated
targetOut = (current - stated)/1200 × prevBase = seriesOutflow - stated/1200 × prevBase
delta     = stated/1200 × prevBase          // POSITIVE = a reduction
```

**So the only thing that can differ between a correct fold and a naive one is
`prevBase`** — and it differs in both the rate the user reads and the delta
written into the event.

**The one term that is the whole build:**

```ts
base = Math.max(0, base + (m.inflow ?? 0) - (seriesOutflow - delta));
```

The roll-forward subtracts the **adjusted** outflow, because that is what the
engine will have applied by then. Using `seriesOutflow` there is the naive
error: month 1 is identical, and every longer ramp drifts from the stated rate
while still looking right.

### The contract tightened mid-build

The first version took an `openingBase` and rolled forward to the ramp's start.
That was a **second place computing a number the series already carries** — and
therefore a second place for it to disagree with the engine. It now takes
`prevBaseAtStart`, which the caller reads directly from the scoped series'
previous row. Fewer moving parts, one source for the denominator.

### Absence, named and ordered

`'seed-unknown' | 'no-prior-month' | 'prev-base-zero'`, in that precedence.
**Seed outranks the others** because without it there is no base at all, so
naming a different reason would name the wrong one. An absent month contributes
**no event** and still rolls the base on the unadjusted series — it stated
nothing, so it changes nothing.

## 3. The UI

A **third arm** on the amount toggle, rendered only when
`newEvent.scenario === 'Outflow'` — the draft already knows its IBRO type, so no
new plumbing.

**Selecting it clears the stale amount** (the `:3490` precedent: subscribers and
a rate are not the same number) **and clears the spread explicitly**. Churn mode
*replaces* the spread with its own months control, and the percentage arm's own
comment records what silence there costs — a spread left enabled from an earlier
draft persists invisibly and still applies on Add.

The panel shows the **current rate** for the slice, read from the same series the
fold reads — one series, two uses, so the figure on screen and the figure in the
event cannot disagree. Then target (points), months, and the **per-month grid**
binding **cumulative** stated reductions, prefilled linear and editable. **No
sum-to-100 machinery**, because there is nothing to normalise: 1/3/6 stays 1/3/6.

**Absent-with-reason** on every absence condition, and **Add is gated with a
named reason** — the `pricingDraftBlockReason` precedent: say why, never grey
something out silently.

### A defect caught while building

My first insertion of the panel closed the toggle container early and swallowed
the amount input in a `<div className="hidden">` to balance the JSX. That would
have hidden the ordinary amount input in **every** mode, not just churn — a
structural convenience that silently broke the path it was not about. Restructured
so the input renders exactly when it means something, and pinned by a check.

## 4. The bar

Churn rows join the barred class **at the `:512` rule**, before the percentage
branch, declining with a stated reason through the existing mechanism.

The reason is sharper than the percentage one. Group-edit reverse-engineers a
ramp by summing `|subscriberVolume|`. On a percentage row that arithmetic is
meaningless. **On a churn row it succeeds** — the figures are quantities — and
yields a total that is not a churn statement, which re-spread by shares would not
reproduce the stated rates. A plausible, wrong spread with nothing about it to
look wrong.

The spec pins that the branch **precedes** the percentage branch and that there
is **exactly one** churn bar, honouring the source comment beside it: a clause
placed where it cannot fire protects nothing, and a mutation test proved it.

## 5. The summariser

`volumeEventSummary` gains a churn branch reading **stored figures only** —
`Churn 24.5% → 21.5%`. Describe, never re-derive: the row is a save-time record
and the base has moved since. The R4 table and Compare's per-file panels inherit
the sentence without knowing churn exists.

## Where things stand

**R7 ships as one mode with no one-off/recurring fork** — a single month is a
ramp of length 1, and the spec asserts it takes the same path.

**The held tail is open**, per decision 3: whether the last stated reduction
persists beyond the ramp, or more fold months can be added. Alessandro's
question; nothing in this build forecloses either.

**Open:** DQ, which EXPECTED.md records as next; the yield pass's private scope

## Limits of this check

**Nothing is mounted.** The fold, the carrier, the seams and the summariser are
driven directly. The card — the third arm, the panel, the grid, the block reason
— is **source-read**, with every check named as such. That an Outflow draft
actually shows the arm, and that the grid renders the derived column, has not
been observed.

**No real save was round-tripped through the card.** The round-trip spec drives
the real writer and reader through real xlsx, but no churn event has been created
in the app and re-loaded.

**The fold's inputs are trusted, not verified end to end.** That
`'Outflow (Adjusted)'`, `'Inflow (Adjusted)'` and `'Base (Adjusted)'` are the
right keys on the scoped series is read from `computeAdjustedForecast`'s row
construction; no check exercises the card's mapping from that series into
`ChurnSeriesMonth`. If those keys were wrong the fold would receive zeros and the
absence path would fire — visible, but as the wrong reason.
