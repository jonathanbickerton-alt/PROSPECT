## Item 3 — the fix

**`forecastCoverage(event, metric, month, viewLeaves)`** in `forecasting.ts`,
preferred over `eventCoverage` for percentage events:

```ts
coverage: e.amountType === 'percentage'
  ? (forecastCoverage(e, metricOf(e), month.month, viewLeafForecasts)
     ?? eventCoverage(e, viewScope, leavesFor(e)))
  : 1,
```

**A ratio, not a direct sum**, because `applyEventsToMonth` owns
`pct × basis × coverage` and the basis depends on `percentageBasis`. Since a
derived view's forecast **is** the sum of these leaves, the baseline case reduces
exactly to `pct × forecast(view ∩ target)` — the decision's wording.

**`null`, never `0`, when it cannot answer** — no leaves supplied, or a view
whose forecast for that metric-month is zero. Answering 0 would silently discard
the event, which is the failure being removed. A **stored** forecast returns no
leaves at all: it was fitted, not summed, so its leaves do not add to it and
weighting by them would be a second wrong denominator in place of the first.

**The wiring**, four files: `resolveFromStore` returns `leaves` at all **four**
return sites; `App.tsx` widens `resolveForecast`; `ForecastContext` widens the
type (`leaves?:` — optional, so the mounted harnesses that supply their own
resolvers still typecheck); `WhatIfTab` resolves the view's leaves through
`resolveEventScopeForecast` — the same seam the event-scope surfaces use, so the
chart cannot disagree with them about what a view is made of.

**After, on the walk's save:**

## Limits of this check

**The walked `+0.00` has still not been reproduced on any supplied file.** Both
saves give a non-zero coverage at the aggregate (0.0129 on the 02 Sep file). What
is reproduced, twice and on real fitted data, is the *divergence* the fix
removes. If the screenshots showed an exact zero, the remaining candidate is a
leaf with a forecast but no historical rows of the metric — which the fix now
covers by construction, but which I have not observed.

**The fix is verified through the engine, not in a browser.** `deriveAggregate`
and `computeAdjustedForecast` are the same functions the chart calls, and the
leaves are resolved through the same seam, but no page was rendered this session
and the wiring from context to card is asserted at source.

**`viewLeafForecasts` is empty for a STORED forecast**, so a fitted aggregate
keeps the historical weighting and its percentage events still diverge. That is
deliberate and pinned, not an oversight — but it means the fix reaches derived
views only. Whether a fitted aggregate should be excluded from the rule at all is
a question this session did not open.

**Item 3's second clause is unbuilt** — see the shed note. `appliedEventIds`
still records a zero-coverage event, so the caption can still print "1 applied"
beside a zero delta at a view where nothing moved.

**The mounted harnesses are unaffected but unexercised on this path.** They
supply their own `resolveForecast` without `leaves`, which is why the context
type makes it optional; every such caller therefore takes the historical
fallback, and the new path is exercised by the new spec rather than by them.

Two things are worth keeping from this. First, **the control earned its
