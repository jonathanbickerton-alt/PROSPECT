## Item 3 — the mechanism

Not the matcher, not an 'All' marker, not the applicability filter, and not the
seed gate. **`eventCoverage` and the percentage basis are drawn from two
different quantities.**

```
HISTORICAL — what eventCoverage weights by, summed from the DATA ROWS
  metric(view ∩ target) =    13,859.00
  metric(view)          = 1,070,993.00
  ratio                 = 0.012940327     <- the coverage actually used

FORECAST at 2026-09 — what the percentage BASIS is drawn from
  forecast(view ∩ target) =    482.81
  forecast(view)          = 31,839.87
  ratio                   = 0.015163693   <- the ratio the arithmetic needs

THE TWO RATIOS DIFFER BY 17.18%
  aggregate delta = 14.8% × 31,839.87 × 0.012940327 = 60.98
  leaf      delta = 14.8% ×    482.81               = 71.46
```

`eventCoverage(event, cohort, leaves)` weights by `leaf.volume`, and
`computeAdjustedForecast` builds those leaves by summing **`wiValueCol` over the
loaded history rows**. The basis it multiplies is `month.inflow.mean` — a
**fitted forecast** for one month. The module promises:

> Reconciliation holds by construction: each leaf takes the same percentage of
> its own value, and those sum to that percentage of the aggregate.

That holds only while `forecastLeaf / forecastTotal == histLeaf / histTotal` —
only while the fit preserves the historical mix exactly. **It does not**, because
each leaf is fitted independently: 24 months of Holt Linear moves the mix. On
this save the drift is 17.18%, and the aggregate is wrong by that fraction.

**This is also why 1456 could not reproduce it.** That probe built its own
`baseForecast` with `monthlyInflow(...)` drawn from the same data rows the
coverage weights come from, so the two ratios were equal *by construction* and
the reconciliation held perfectly. The bug is invisible to any fixture whose
forecast is proportional to its history — which is every synthetic fixture in
this repo.

### And it degenerates to the walked shape

Coverage is `inBoth / inView` over **historical** volume. A leaf with a fitted
forecast but **no historical rows of that metric** contributes 0 to `inBoth`
while contributing its full forecast to the basis — coverage 0 at the aggregate,
coverage 1 at the leaf, and exactly the walked "+0.00 at All, full at the leaf".
**On this save no such leaf exists (measured: 0 of 72)**, which is consistent
with this save not being the walked one.

## Item 4 — the fix

### The engine fix is NOT made, and the reason is not budget

Item 4 offers two branches. **Neither is the mechanism.** The matcher does not
drop the leaves — coverage is non-zero and the scope matches. The stored scope
does not match "NO populated leaf" — it matches one, with 13,859 historical
inflow.

The correct repair is to weight coverage by the **forecast** volume for the month
being applied, not by historical rows. That cannot be done "at ONE site":
`computeAdjustedForecast` holds the aggregate's forecast and the raw data rows —
**it does not have the per-leaf forecasts**, which is precisely what a
forecast-weighted coverage needs. Supplying them means changing what the adjusted
path is given, and it changes what a percentage event *means* at an aggregate
(historical mix versus forecast mix — they are different claims about the same
event).

**That is a decision, and per the brief's own STOP clause it is Jon's.** A fix
whose shape the brief did not anticipate, made inside a session that could not
reproduce the reported symptom, would be exactly the change nothing can check.

### The caption half IS done — it is a settled decision and one site

> the "N events applied" caption counts events applied AT THIS VIEW
> (decision, Jon 2026-09-02), not `marketEvents.length`

```ts
- return { baseDelta, arpuDelta, eventCount: marketEvents.length };
+ const appliedHere = new Set<string>();
+ for (const m of adjustedMonths) for (const id of m.appliedEventIds ?? []) appliedHere.add(id);
+ return { baseDelta, arpuDelta, eventCount: appliedHere.size };
```

Counted from the engine's own `appliedEventIds`, in the same pass that produced
the deltas, rather than re-derived beside them. The memo now depends on
`adjustedMonths` rather than on an array length, so a filter change re-counts.

**Why this is worth doing on its own.** The old caption printed the same number
at every view and so could never disagree with the two figures beside it. In the
walk it printed *"1 event applied"* next to a +0.00 delta and was read as
corroboration that the event had reached the aggregate. It corroborated nothing —
it would have printed 1 at a view the engine never touched. **A caption that
cannot be wrong cannot be evidence**, and this one was quoted as evidence.

### The reconciliation spec the brief asks for CANNOT BE WRITTEN GREEN

The brief asks for a mounted spec asserting *"the All delta equals the leaf delta
to the penny"* on a filter change. **Today that assertion is false on any fixture
whose forecast is not proportional to its history** — 60.98 against 71.46 on

Writing it green would mean choosing a fixture that hides the defect. Writing it

absence is the sharpest statement of the finding**: the reconciliation the module
promises does not hold, and no honest spec can say otherwise until the decision

## Limits of this check

01 Sep 23:37; the brief describes Corporate / Mobile Voice / Direct with +8.00K

forecast volume but no historical rows would give coverage 0 follows directly
from `inBoth / inView`, and it matches the walked shape exactly — but this save
contains no such leaf (0 of 72, measured), so I have not seen it happen.

**Nothing was driven in a browser.** The reproduction is through
`deriveAggregate` and `computeAdjustedForecast` with the real save and the real
fixture, which is the same path the chart uses, but no page was rendered and the
caption fix is asserted at source and by the engine rather than by a screenshot.

`test-data/Walks/` is not gitignored, so `git add -A` would have put it in
history permanently. Committing it is Jon's call; the report cites it by sha1 so

**`deriveAggregate` was fed leaves rebuilt from the save's sheet, not from the
app's import handler.** The sheet is what the handler reads and every field was

so a difference in how it assembles a leaf would not show here.
