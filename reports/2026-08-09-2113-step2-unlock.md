## Diagnosis

### The predicate, quoted

```ts
const hasLegacyBaseline = Object.keys(savedForecasts).length > 0;   // App.tsx
<StepIndicator hasBaseline={hasLegacyBaseline} ... />
```

and inside `StepIndicator`: `if (!hasBaseline) return 'locked';`

**It reads neither `forecastData` nor `baseForecast`.** Both hypotheses in the
brief were reasonable and both are wrong, so Session L's derivation change and
the keep-last retirement are exonerated. `git show <commit>:src/App.tsx` returns
the identical line at `d4a7f8a`, `ec77b34` and `c161a42`.

### Why generation stopped satisfying it

`savedForecasts` is written from `newForecasts`, which comes from the **Standard**
cohort workers. A scoped leaf run sets `targets = []`:

```ts
const targets = options?.restrictToLeafKeys
  ? []                       // a scoped leaf run enrols no Standard cohort
  : options?.cohortIds ? ... : missingStandardCohorts;
```

So bulk leaf generation writes `forecastStore` and nothing else.

## The fix

```ts
export function hasAnyUsableForecast(store, hasLegacy: boolean): boolean {
  for (const [key, bf] of store) if (!isRetiredAggregateFit(key, bf)) return true;
  return hasLegacy;
}
```

Derived from **store contents** — the corollary of surface-not-store: a gate
reads what exists, not what a transient path populated, and not which door
produced it.

- **Retired aggregate fits do not count.** The seam refuses to return one, so a
  store of only those can serve no view; unlocking on it would have the indicator
  claim coverage the reader cannot reach.
- **The legacy store stays admissible** as the second clause, for pre-bottom-up
  sessions whose forecasts live only there. It is no longer the first.
- **State-not-navigation.** `forecastStore` survives selection changes, tab moves
  and restores, so the gate cannot flicker.
- Pure and exported so the spec **drives** it rather than re-implementing it.

### A duplicate predicate, collapsed

`noForecastReason` had its own `forecastStore.size > 0 || hasLegacyBaseline`,
which disagrees with the gate in exactly the retired-fit case — size non-zero,
seam serving nothing, filter bar offering a widen-the-filter hint where the
honest answer is the Step 1 link. It now reads the same value. Introducing a
canonical predicate and leaving a hand-rolled twin beside it is how the two-store
relationship reached three findings.

### Copy

"The forecast will appear here once generated. **Save it to unlock Step 2.**"
described a save that has never existed. Replaced by an additive key naming the
true rule. **The old key was left in the locale files rather than edited**, so a
locale carrying a translated version of the wrong sentence is not silently
repurposed into asserting the right one under a translation nobody re-checked.
Audited: it was the only save-a-forecast reference on that surface.


The control matters: without "with nothing generated Step 2 IS locked", the
unlock assertion would pass for an indicator that never locks at all. The restore
case rebuilds a **new Map**, because a restore does not hand back the identical
object and a gate keyed on identity would pass here wrongly.

## Recorded, not fixed — needs a decision

**A new upload clears no store.** Demonstrated by the gate with real functions: a
store holding an old cohort's fit, against a `leafMap` from newly uploaded data,
gives `hasAnyUsableForecast === true` while the new data's own cohort resolves to
`null`. **Step 2 reads unlocked for data that has no forecasts.**

**Pre-existing, and this fix did not widen it** — the old gate leaked the same
way via `savedForecasts`, which `handleFileUpload` also never clears. What
changed is which store leaks, not whether one does.

Not fixed here because the obvious remedy — clearing the stores on upload —
destroys generated work with no warning and no undo, which is a product decision
rather than a correctness one. Three options are recorded in EXPECTED.md.

### Declared gaps

Stage 3 drove the `StepIndicator` end-to-end through the real component and the
real predicate; **App's wiring of `hasAnyForecast` into that prop is verified by
source-pattern match, not by mounting App itself.** Both halves exist and neither
covers the other.
