## What shipped

### 1. One effective-rate definition

`promoEffectiveArpuMap(tierData, override)` — override-if-present by PRESENCE,
so a stated `0` beats the derived figure and a stated negative is carried
verbatim.

**Module-level, not a hook, and that is the point.** The card and
`buildPromoEvents` call the same function. The write path previously built its
own `tierArpu` from `t.baseArpu` alone, so a card showing a stated rate would
have saved an event blended from the derived ones — the two-baselines defect
trap 65 exists for, arriving on a third surface (Finding B). One shared function
makes that impossible rather than merely tested for.

**`mixConstraint` was not touched.** `perMemberArpus` is already the engine's
input; the whole change is which map is handed to it. The brief's instruction —
*if you are editing mixConstraint, the wiring is wrong* — held as a useful
tripwire and never fired.

**The sign guard is upstream, not crossed.** `computeTierData` clamps with
`Math.max(0, …)` when scaling to a forecast month, so a *derived* rate cannot be
negative. That clamp runs before this function, and this function **replaces**
rather than adjusts, so a stated −4.25 reaches the engine as −4.25. The spec
asserts it rather than trusting the reading.

### 2. The input

The read-only Base ARPU span is now an input, on the R2 pattern: derived figure
as **placeholder** (never pre-filled — a filled box reads as a stated rate),
edited-vs-default styling driven by presence, clearing deletes the key and
returns to derived-today, stated zero distinct from unset, negatives verbatim.

`data-testid="promo-band-arpu-override-<band>"`, matching the R2 convention.

**No new i18n keys.** Finding A's resolution is a *reuse*: the R2 key already
names the real basis correctly in all six locales, so the correct copy was
already translated. Adding a key would have meant six new translations saying
something the existing six already said.

### 3. Draft state, and why it needs no protection

`draftPromoBandArpu`, cleared by the reset and seeded by both edit-restore
handlers from the stored `promoBandArpuOverride`.

**The no-`seedMixPreserving` rationale, re-established this session rather than
inherited from the reverted attempt:**

`draftMix` needs preserving because it must carry an entry for **every** member
— shares sum to a fixed total — so an effect rebuilds it from the tier list
whenever that list changes, and it was that rebuild which wiped a restore. This
map is **sparse by design**: absence per band *is* the carrier, nothing has to
cover the members, so no effect rebuilds it and there is no rebuild to protect
against. Its writers are exactly four: the input, the two restore handlers, and
the reset.

**It holds.** Stale keys are possible — switch the mix axis with a rate typed —
and are harmless: the effective map iterates the current members, and the write
path filters them. Keeping rather than clearing them means switching axis and
back returns the user's typed rates, which is what presence-as-carrier should
do.

### 4. The write path

`promoStatedRatesForMembers` filters the persisted map to current members and
returns `undefined`, never `{}` — a map naming only stale bands states nothing
about the event, and absence is the carrier (Finding E).

Wired at **all three** `buildPromoEvents` call sites with all three dependency
arrays updated; the counts were asserted in the patch rather than eyeballed,
per the fifth-writer lesson.

### 5. The mounted spec — and the check that could not fail

Extended `scripts/mix-card-spec.tsx` rather than adding a harness, per Finding
D: **42/42 → 73/73**.

Transitions driven through the real input: unset shows the derived placeholder
and names its source → type an override → styling flips **and the blend moves**
→ clear → derived returns and styling reverts → stated zero styles as edited and
moves the blend **down** → negative is carried verbatim and pulls below the
stated-zero blend → Add → the captured event carries the typed rate → through
the **real** `marketEventExportRow` → back through the **real**
`readStoredEventModifiers`.

**The first run failed four checks, and one of them mattered more than the
other three.** *"Styling flips to edited-vs-default"* tested
`/border-\[#e60000\]/` — but the input's base class carries
`focus:border-[#e60000]` in **both** states, so the pattern matched always. The
check passed on its first run **vacuously**, and would have kept passing with
the styling entirely removed.

It is re-aimed at `bg-[#e60000]/5`, which exists only in the overridden branch,
and paired with a negative assertion on `text-slate-400` for the unset branch.
Recorded here rather than quietly corrected: **a check that cannot fail is worse
than an absent one**, because it also reports that the ground is covered. The
other three were a band name read *after* the Add click had reset the draft —
read before it now.

Two function-level checks cover the stale-key filter, because the harness has no
tariff axis available and the axis switch that creates a stale key is therefore
not drivable through this mount. Labelled as such in the spec, with the expected
values written by hand rather than computed with the function under test.

### 6. Guard-trap 67

Makes the **derived** rate always win inside the one effective-rate definition.

Planted where the heuristic is weakest, and this is the nastiest shape the
capability can fail in: the override is still stored, still exported, still
restored on reopen — and simply never read. **Every carrier-level check stays
green.** The map round-trips perfectly and the number the user typed never
reaches the blend or the saved event. Only a mounted transition catches it,
which is why the trap points at the mix-card spec rather than a round-trip one.

### 7. Guard-trap 64 went MISSED — an anchor this change made ambiguous

The first full guard-traps run returned **64/65**, and the miss was **trap 64**,
which has nothing to do with R3: *"clearing the tier override stores zero instead
of unsetting"*, on the **Value** card.

**Nothing regressed in the product.** What broke was the anchor.
`spec:yield-roundtrip` asserted the WhatIfTab source `.includes("if (raw === '')
delete next[tier];")`. R3's new input uses that clear-idiom **verbatim** — as it
should, it is the same semantics — so the string acquired a second owner. Trap
64 deleted it from the yield site, the assertion still found the promo one, and
the spec stayed green.

That is the stale-anchor rule firing exactly as written: *a change that rewrites
the ground under an assertion must re-aim it in the same commit*. Here the
change did not rewrite the line, it **duplicated** it, which is the same failure
reached from the other direction and is easier to miss because the original site
is untouched.

**Re-aimed to counts.** Both that check and the placeholder check beside it
(`placeholder={formatNumber(baseArpu)}`, ambiguous for the same reason) now
assert **exactly two** sites. If either input loses the idiom the count drops and
the spec fails; a third input arriving also fails, which is correct — it should
be a deliberate update rather than a silent widening of what the check covers.
Re-run: **65/65**.

**Why this is worth the space.** Both instrument defects this session found were
of the same species — a check that passes for a reason unrelated to what it
claims. The vacuous styling check passed because its pattern was always present;
trap 64 passed because its anchor was satisfied by a different site. Neither was
found by reading the checks; both were found by running them against a
deliberately broken tree. That is the argument for guard-traps existing, and it
is the second session running in which the traps caught an instrument rather than
a defect.
