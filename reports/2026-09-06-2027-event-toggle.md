## What was asked

Alessandro, in UAT: a user builds up a set of events and then wants to try a
subset. Today the only way is to delete an event and add it back, which loses
the event. The ask is a switch.

## The one predicate

`isEventOn` in `src/utils/forecasting.ts` is the only place `.enabled` is read
for an apply decision. It is short enough to quote whole:

```ts
export function isEventOn(e): boolean {
  if (!e) return true;
  if (e.enabled === false) return false;
  return e.Enabled === undefined || e.Enabled === null || String(e.Enabled) !== 'No';
}
```

Three things about it are deliberate.

**Absent means ON.** Only an explicit `false` turns an event off. Every event
in every workbook saved before today has no flag at all, and what those files
mean is "all of these apply". A nullish check would have read absence as off
and silently disabled every event in every existing save on open. That is
trap 146, and it is the trap that would have cost the most.

**It accepts two shapes.** The What-If engine holds typed `MarketEvent`s with
`enabled`; Compare's engine holds RAW SHEET ROWS and never calls
`marketEventFromRow`, so its flag arrives as the `Enabled` column. Decision 8
put the check at the engine rather than the parser precisely so a disabled
event stays listable in the panel — which means the predicate has to read both.
A typed-only predicate would have left Compare's four sites covered by nothing.

**`enabled`, not `disabled`.** Every other flag on these carriers is named for
its positive state, and a negative name inverts every read site.

## Twelve apply sites, six display sites, pinned apart

The twelve are counted by their `REQ-D6-01, apply site` marker rather than by
counting `isEventOn` calls, and that distinction is the point: the display
sites call the predicate too, so a count that could not tell them apart would
go green if an apply site were quietly converted into a display one.

The six display sites are decision 7, not decision 1 — the tooltip's three
carriers, the chart's month markers, the retention warnings, and the churn
exclusion set. They are pinned by their own separate count, so moving a site
from one class to the other is a visible change rather than a silent one.

The third pin is zero-occurrence: nothing outside the predicate and its three
export writers reads `.enabled` at all. This is the shape that cost three
sessions when the re-banded pool carried its own copy of a scope rule, and the
shape `eventScopeMatchesView` was extracted to prevent.

## The switch

`src/components/EventOnOffSwitch.tsx` — one component, `role="switch"` with
`aria-checked`, testid `event-on-<id>`, keyed labels in six locales.

`role="switch"` rather than a checkbox because assistive technology then
announces on/off rather than ticked/unticked, and because the indeterminate
state has a defined ARIA value (`"mixed"`) that a checkbox's `indeterminate`
DOM property does not expose to the accessibility tree at all.

In `EventsSummaryTable` the switch column comes **first**, because it decides
whether the rest of the row applies. Off rows are greyed by one class, not
hidden. `onSetEnabled` is optional, and its absence is exactly Compare's case:
Compare lists a disabled event greyed but owns no state to change, so it gets a
static indicator rather than a control nobody can honour.

## A finding, not a build

The brief's item 4 named the pricing self-exclusion at `WhatIfTab.tsx:~2989` as
needing to ignore disabled events. It does not. That seam computes its baseline
through `computeAdjustedForecast`, which is where apply sites 1–8 live, so a
disabled pricing event is already absent from the blend the draft is measured
against. A filter there would have been a **thirteenth** place deciding what
"off" means, which is the exact thing the pin exists to keep at twelve.

The self-exclusion's own `p.id !== excludeId` stays: it answers a different
question — "is this event me", not "is this event on". The reasoning is
recorded at the site.
