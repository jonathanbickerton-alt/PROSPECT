## 1. What D5-05 barred, and why HELD is different

D5-05 barred **any** campaign containing a percentage row, for one reason: the
group edit reverse-engineers a ramp by **summing `Math.abs(subscriberVolume)`**
across the rows, and a sum of per-cents is meaningless.

A held campaign never reaches that arithmetic. Its restore — session 1's, and
no new function — reads the **target off the LAST row** and the **ramp length
off `holdPlateauStart`**, with the toggle taken from the **Hold column** and
never inferred from the shape. The hazard has not lapsed; it is avoided by
never reaching the summing path. That is exactly the shape in which the churn
bar was lifted under D5-REVISED, and the amendment says so in those terms.

**Why EVERY row and not some.** The clause says "every row `hold`", and the
predicate is `g.rows.every(e => e.hold)`, not `.some`. Target-from-the-last-row
and length-from-the-plateau are both statements about a series that plateaus. A
campaign with a held head and an unheld tail is neither shape, so it stays
barred rather than being restored as a shape it is not.

### The bar was the only blocker — and two things behind it were not

Lifting `anyPercentage` to `anyPercentage && !allHeld` was enough to route both
pills, because both render purely off `group.editable` and
`editCampaignFromVolumeTable` already answers "which editor owns a promotion"
in one place (D5-04). **No new function, exactly as the brief requires.**

But two defects sat behind that bar, unobservable while it stood because the
branch could not be reached. Both were found by driving the app, not by reading:

**(a) The campaign restore dropped the percentage fields.** The hold branch's
`setNewEvent` carried no `amountType`, `percentageBasis` or `retentionLinked`.
`handleEditStart` — the single-row path — says of exactly those three fields
that *restoring them is not optional*, because without them a percentage event
reopens and re-saves as absolute and **the amount changes meaning from 10 per
cent to 10 subscribers**. The campaign path had never needed them. It does now.
The amount control is set alongside them, so the `%` arm is lit: a draft that
saves per-cent behind a lit "Subs" arm is a screen disagreeing with itself.

**(b) `handleSaveCampaign`'s rebuild dropped the same three.** Caught by the
re-save assertion, which failed on the first full run. The rebuild's arithmetic
*already* respected `isPctAmount` and skipped the rounding — so the figures
would have stayed per-cent while the stored type said subscribers, which is
worse than either being wrong alone. Both sites now write what the add path has
always written.

Neither was speculative: (a) was reasoned from the existing comment and (b) was
handed over by a red assertion.

**Case (2) is built on the Promotion card, and the reason is worth recording.**
With hold OFF the Volume card **hides** its spread control for a percentage
draft — REQ-D6-03 settled that ambiguity — so a multi-row unheld percentage
campaign is not reachable there at all. The Promotion card's ramp is open for
percentages either way, so the unheld case lives where a user could actually
create it. Asserting it on the Volume card would have meant asserting against a
campaign no user can build.

**The decline is asserted on rendered TEXT, never a title attribute**, as the
brief directs — a tooltip is invisible on touch, which is the defect D5-05's own
render note records.

**Case (4) exercises what `promo-hold-mounted` had declared unreachable.** That
file records finding "neither a pill nor a decline reason" for a promo campaign
on the Volume tab, so D5-04's router was not covered by it. The cause was a
harness fault, not the app: a plain `btnByText('Volume')` matched a **different**
button — the card also renders a measure control labelled "Volume" — and `.find`
returned that one, so the click did nothing and the case read the Promotion
card's own table while believing it was reading the Volume table's. Taking the
tab from the tab strip fixes it, and the route asserts clean.

**Two controls are found structurally, and named here because that is a
dependency.** The Volume card's amount box, its ramp-duration box and its unit
arms carry no testids; the campaign-save button carries none either. They are
found by the percentage placeholder, the min/max pair, the lit-arm class and the
resolved save label respectively. **No testid was added**: that is a UI change
this brief did not ask for, and the label lookup is honest about what the user
actually presses. The cost is that a copy change to those labels breaks the
spec, which is a real and stated fragility.

## Limits

- **One cohort, one fixture.** Corporate on the trimmed fixture, a 24-month
  horizon, campaigns starting at `MONTHS[0]`. The restore rule is asserted on
  that shape; nothing here varies the segment or the start month.
- **The ramp is 3 and the target 10 in every case.** `holdPlateauStart`'s own
  edge cases — a one-month ramp, a custom distribution passing through its
  target early — are covered by `spec:hold-shape`, not here. This file tests
  the ROUTE, not the arithmetic it routes to.
- **Nothing was run against a browser.** Every drive is JSDOM.
- **The mixed case is barred, not measured.** A campaign with some rows held
  and some not stays barred by `allHeld`, and no assertion drives one — the app
  offers no way to build one from a single card, so a spec for it would have to
  fabricate rows the UI cannot produce. Declared rather than claimed.
- **Case (2) proves the unheld bar on the PROMOTION carrier only.** The Volume
  card cannot build an unheld multi-row percentage campaign at all (§2), so the
  Volume-side unheld decline is unexercised by construction, not by omission.
