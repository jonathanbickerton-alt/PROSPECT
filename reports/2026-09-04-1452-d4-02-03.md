## Item 1 — D4-02, the numeric echo

`MixSliderRow`'s numeric input becomes `MixPctBox`: a local draft while focused,
committing on **Enter or blur**, `Escape` restoring the committed value. The
commit calls the same `onChange` a drag does, so the wall applies at commit
exactly as at the end of a drag.

**A separate component**, because it owns state and `MixSliderRow` does not —
the row is a pure render of what the card hands it, and a draft inside it would
give every row's identity a lifetime it did not have.

Two behaviours worth stating, because neither is obvious from the decision:

- **A blank or unparseable box is a CANCEL, not a zero.** `Number('')` is 0, so
  committing it would silently empty a tier the user was part-way through
  typing.
- **The box follows the card unless the user is mid-edit.** `useEffect` on the
  committed value clears the draft, so a drag elsewhere updates the box — but a
  draft in progress is the user's until they commit or cancel.

### A failure in my own simulation, not the control

`(i) BLUR commits` failed on the first run. React implements `onBlur` through
the **bubbling `focusout`**, not `blur`, so a non-bubbling `blur` event never
reaches the delegated listener. The control was correct; the spec was dispatching
an event React does not listen for. Fixed in the spec, with the reason recorded
there.

## Item 2 — D4-03, exactly determined

### The existing wording does NOT fit, so one key was added

`whatif_mix_range_collapsed` reads, in English:

> The holds leave one reachable blend, so the sliders cannot move:

and the same in all six locales — de *"Die Haltungen lassen…"*, es *"Las
fijaciones dejan…"*, fr *"Les blocages ne laissent…"*, it *"I blocchi
lasciano…"*, pt *"As fixações deixam…"*. Every one of them attributes the
collapse **to the holds alone**.

Under D4-03 the cause is the **target and** the holds. With one hold and a
target the sentence names the wrong cause; with a target and *no* holds it would
be plainly false. So it does not cover the case, and reusing it would have made
the card state something untrue.

**`whatif_mix_exactly_determined`**, added in all six locales, keeping each
locale's established term for target and the existing sentence shape so the
value can follow it:

> The target and the holds leave one reachable mix, so these sliders cannot
> move:

`spec:i18n-parity` is **194/194** with it.

### The engine decides, the panel draws

`exactlyDeterminedUnderTarget` is a **read** in `mixConstraint.ts`, derived from
the same feasible-interval arithmetic `rebalanceToTarget` uses rather than
restated: a member is fixed exactly when asking to drag it to 0 and to 100 both
return the same share. The two therefore cannot disagree about what a single
point is.

`MixTargetPanel` still computes nothing. It takes `exactlyDetermined` as a prop
and renders it **ahead of the wall**, with the wall suppressed while it holds —
a mix with no move to make cannot also have had a move stopped.

## Limits of this check

- **The draft is discarded when the card moves the share.** A user typing in one
  box while a drag elsewhere changes that same row loses the draft. That is
  deliberate and stated in the code, but it is a behaviour nothing asserts.
- **Escape is checked once, on the Value card only**, and blur likewise. The
  Promotion arm's box is checked for draft-then-Enter, not for the full set.
- **`exactlyDeterminedUnderTarget` costs two solves per free member.** It runs
  in a `useMemo` on every mix change; nothing here measures that cost, and on a
  10-15 slider tariff axis it would be 20-30 solves per keystroke.
- **The determined case is exercised at three tiers with one lock.** The
  equivalent state on a wider axis - many members, several holds - is not
  reached by any check here.
- **No check asserts the determined REASON's text**, only its testid. The
  collapsed-range check next to it does read the locale string; this one does
  not, so a wrong key would still pass.
