## Item 4 — spec:trap-anchors

### The first run found 10 failures, not the 0 the brief expected

Two of those causes were mine, one was real, and separating them was the work.

**Cause 1 — my extractor was too narrow.** Anchors live inside `mutate`
closures, not as fields, so they are recovered by instrumenting
`String.prototype.replace` while each `mutate` runs against its own pristine
file. Five traps never call `.replace`: they splice by index —
`indexOf` the start, `indexOf` the end, `slice` between. Capturing `indexOf`
too removed those five, and they were never defects.

**Cause 2 — I counted terminators as anchors.** Trap 18's second `indexOf` is
`'.forecast : null);'` searched *from* an offset, and that string occurs **175
times** in `App.tsx` quite legitimately. A relative terminator does not need to
be globally unique; demanding it was the check being wrong. Only an
UNPOSITIONED search is an anchor, and the dump now records that distinction.

**Cause 3 — six anchors genuinely occur 2–3 times.** That is real, and it is
what the check exists to find.

### The six, recorded rather than fixed

| trap | file | occurrences |
|---|---|---|
| 22 the cohort-months label loses its grain | `ForecastVsActualsTab.tsx` | 2 |
| 24 the blocked state collapses into covered | `App.tsx` | 2 |
| 26 the error banner survives a selection change | `App.tsx` | 2 |
| 51 a restored session drops its saved historical months | `App.tsx` | 3 |
| 102 the churn add falls behind the spread gate | `WhatIfTab.tsx` | 3 |
| 124 the forecastType identifier is translated | `App.tsx` | 2 |

All six are CAUGHT by the harness today, so each plants somewhere effective.
What none can prove is that it plants where its author intended, and a line
inserted above any of them would move the trap silently.

**I attempted to fix them and reverted.** Extending five anchors in one pass
broke trap 22 outright — it went from "2 occurrences" to "ZERO, the anchor has
aged out", which is a worse state than the one I was correcting. The registry
was restored to its committed form and the anchor-dump re-applied.

**A decision surfaced there, and I did not take it.** Adding a RED spec to the
positive control would make every future guard-traps run INCONCLUSIVE and block
the gate entirely. The three options — fix the six now, exempt them, or leave
the spec out of the control — are a decision about the gate, so instead the
project's existing mechanism is used: an **exact-count baseline**, each of the
six named with its count.

**The baseline is exact in BOTH directions.** A seventh fails, which is the
point. And *fixing* one also fails, forcing the list to be updated rather than
letting it quietly describe a state that no longer exists — an allowlist that
can only grow is the "exemption wired to nothing" this project has already paid
for once.
