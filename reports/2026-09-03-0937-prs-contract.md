## Item 2 — the split at forecasting.ts:2853

One predicate was true in two worlds and answered 1 for both. It is now two:

```ts
if (leaves.length === 0) {
  // NO DENOMINATOR. ... Callers resolve this to the legacy all-or-nothing 1
  return null;
}
if (targetIdx.length === 0) return 0;
```

The return type is `number | null`. Both production call sites — `WhatIfTab`'s
`eventShare` and `scenarioHelper`'s — resolve `null` to `1` explicitly, and
both sit behind `eventScopeMatchesView`, so the containment test the old
fallback carried is now upstream applicability, a stricter and shared rule.

### `strictNullChecks` IS OFF — the compiler is not enforcing this contract

Widening the return type to `number | null` produced **zero** TypeScript
errors, which is the wrong answer and worth stating plainly: `tsconfig.json`
sets no `strict` and no `strictNullChecks`.

That is not a footnote here, it is the risk. An unresolved `null` would flow
into `e.subscriberVolume * eventShare(e)`, and `1000 * null` is `0` — the event
silently discarded, which is the exact failure the fallback exists to prevent.
So the resolution is an explicit `v === null ? 1 : v` at both sites rather than
a `?? 1` buried in an expression, and the spec pins what the compiler will not.

Filed for the backlog. Turning `strict` on across this codebase is not a
session's worth of work and was not attempted here.

outside until something multiplied by it.
