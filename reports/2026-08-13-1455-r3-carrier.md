## What shipped

### 1. The carrier

`MarketEvent.promoBandArpuOverride?: Record<string, number>` — bucket label to
the user's **stated** per-band ARPU.

**The two-field shape**, as R2 settled it: the event already carries effective
per-band rates, and this map sits *beside* them rather than replacing them.
Which number the user typed is not recoverable from a blend once the blend is
computed, so a single field would lose the distinction between "this is what the
data derives" and "this is what I said".

Presence per band is the carrier. Absent **entirely** (`undefined`, never `{}`)
when nothing is stated — an empty map is a claim that the user visited the field
and cleared it, which is not the same fact. Negative is verbatim per the
rate-sign rule: a minus is an ARPU below zero, not a reduction from default.

### 2. Write, export, read

- **Write**: `buildPromoEvents` copies the map by presence, and **only when the
  mix arm is on**. An override map without a mix would name bands the event does
  not use.
- **Export**: `Promo_Band_ARPU_Override_JSON`, `''` for absence — the same
  carrier the yield override uses.
- **Read**: `readStoredEventModifiers` gained one line calling the shared
  `readStoredRateMap`. **Extended, never forked.**

That last point is the whole reason both import routes are covered. Market
events have two — session restore and workbook import — and both spread the
result of that one function. A field added inside it reaches both or neither;
a field added at a call site reaches one, which is exactly the shape of the
promo-field defect this arc started by fixing.

**So the pin is on the route count, not the field.** The spec now asserts
`...readStoredEventModifiers(r)` appears **exactly twice** in App. A third
route, or a route that stops spreading, fails the spec — and that is a stronger
guarantee than checking that today's two routes carry today's fields, because it
catches the *next* field too.

### 4. Stale anchors, self-reported

Extracting the writer **broke the spec's own wiring checks** — they grepped
`App.tsx` for each column name, and the names had moved to `forecasting.ts`.
They went red, which is the behaviour the anchor rule wants: a change that
rewrites the lines under a check re-aims it in the same commit.

They were re-aimed from *"App's source contains this string"* to *"the row the
real writer emits has this property"* (`col in emitted`). That is both
stale-proof — moving the function cannot break it — and strictly stronger, since
a column name can appear in a comment but a property cannot appear in an object
that lacks it.
