**The grid, as it stood** (`WhatIfTab.tsx`, the promo spread panel):

**The handler**, meanwhile, called `spreadShape({ …, hold: promoHold, horizonMonths })`.

**`promoHold` appears nowhere in the grid.** So the grid rendered the hold-OFF
share split — `+1,000 / +1,000 / +1,000` — while Add emitted
`1,000 / 2,000 / 3,000` and nineteen more months of 3,000. **The chart reads
the events, so the chart was right all along**, which is why the card and the
chart disagreed rather than both being wrong.

**This is the same defect I fixed on the Volume card in REQ-D6-03 session 1 and
did not fix here.** That session's own report says the Volume preview *"used to
re-implement `pct/total` inline, and a preview that recomputes what the save
computes is a preview that can disagree with it"*. The Promotion card had a
third copy and I left it.

The **Volume card's** preview is the shape to match — ramp rows from
`spreadShape`, plus one summarised tail line at `volume-hold-tail`.

## 2. Derive once, read thrice

`buildPromoEvents` **no longer computes a shape.** Its five spread parameters
(`spreadEnabled / spreadMonths / spreadDistType / customDist / horizonMonths`)
are gone, replaced by one:

```ts
  shape: SpreadShapeMonth[];
```

and the body is now `const shape = p.shape;`. **`hold` stays**, because every
emitted row carries it as a restore field.

The card derives it once:

```ts
const promoShape = useMemo(() => spreadShape({
  months: promoSpreadEnabled ? promoSpreadMonths : 1,
  dist: !promoSpreadEnabled ? [100] : …,
  hold: promoHold,

     promoHold, horizonMonthsFrom, newPromo.date]);
```

**Three readers, one derivation**: the preview grid, the Add button's count,
and `buildPromoEvents` via `shape: promoShape`.

## 6. The lag — measured, changed nothing

On the **20:33 save**, through the app's own resolve path
(`buildRestoredLeafIndex` → `resolveFromStore`), a promotion and a Volume-card
inflow event of the **same shape on the same cohort**, run side by side:

```

emitted rows 22 | first3 1000/2000/3000 | last 3000
SUM 63,000 | SUM excluding the last row 60,000
```

|---|---|---|---|---|
| 2026-09 | 1,000 | **0.00** | 0.00 | **0.00** |
| 2026-10 | 2,000 | 1,000.00 | 1,000.00 | 0.00 |
| 2026-11 | 3,000 | 3,000.00 | 3,000.00 | 0.00 |
| … | 3,000 | … | … | **0.00** |
| **2028-04** | 3,000 | **54,000.00** | 54,000.00 | 0.00 |
| **2028-05** | 3,000 | **57,000.00** | 57,000.00 | 0.00 |
| **2028-06** | 3,000 | **60,000.00** | 60,000.00 | 0.00 |

**The two are identical at every one of the 22 months.** The promo re-banded
pool and `Contract_Length` — the brief's two suspects — are **exonerated**: a
promotion's inflow reaches Base exactly as a Volume-card inflow event does.

**The T+1 rule holds exactly, again.** The campaign's own first month reads
`0.00`; the base delta at month *k* is the sum of every row strictly before it;
and at the last month that is `63,000 − 3,000 = 60,000`.

**+54,000 is April 2028** and **57,000 is May 2028** — two months and one month
before Jun 2028 respectively. The row count is **22, not 24**, because the
campaign starts at index 2 of a 24-month horizon (Jul 2026 → Jun 2028).

**This is the same shape as the 1651 session's finding**: the lag is intact and
the reading is displaced by the horizon's start offset. Nothing was changed.

*Caveat:* the resolved aggregate reports `seedBaseKnown false` and
`seedBaseVolume 0`, so Base here is a pure delta over an unknown stock. That
does not affect the deltas — they are differences of two runs over the same
seed.

## 7. The gate refused its first run — and `as any` is why

```
[INCONCLUSIVE] control. The spec is RED on the unmutated tree.
               Every trap would catch vacuously. Fix the spec first.
```

`spec:view-apply-mounted` **CRASHED**, not failed:

```
view-apply-mounted spec CRASHED — TypeError: Cannot read properties of
  undefined (reading 'length')
    at buildPromoEvents (src/components/WhatIfTab.tsx:667:14)
```

**It calls `buildPromoEvents` directly at the seam, eight times**, and every
call passed the five spread parameters this refactor removed.

**The lesson is sharper than "a spec needed updating".** Making `shape`
required was supposed to be the guard — and it was, for the app: tsc named all
three production call sites the moment the old parameters went. It named
**none** of the eight in the spec, because every one of them is cast:

```ts
    } as any);
```

**`as any` at a spec's call site is a hole in exactly the guarantee a
required parameter makes.** The type caught the app; only the runtime caught
the spec, and only because the harness distinguishes CRASHED from FAILED — a
runner keying on exit code alone would have said "failed" and sent me looking
for a wrong number.

All eight now state a shape explicitly —
`spreadShape({ months: 1, dist: [100], hold: false, horizonMonths: 0 })` for
the single-row cases, `[50, 50]` and `[60, 40]` for the two ramps — which reads
better than the five parameters it replaces. **`spec:view-apply-mounted` is
back to 208/208.**

*Third time in five sessions the positive control has stopped a vacuous
100%-caught figure being printed.*

## Limits

- **The percentage grid rendering is not mounted-asserted.** Case 1 asserts the
  emitted percentage rates; the grid's 2dp rendering for a percentage draft is
  implemented and reasoned but only the absolute grid is pinned by a literal.
- **The tail line's month count comes from `heldRows.length`**, which is the
  emitted tail, so it cannot disagree with the rows — but it is also not
  independently derived, and a wrong shape would produce a consistently wrong
  line.
- **Nothing was run against a browser.** The grid is asserted in JSDOM.
- **§6 is one cohort on one save.** The promo-vs-volume equality is measured on
  Corporate / Mobile Voice with a 24-month horizon; it is not a proof that no
  promotion arm ever diverges — a re-banded Retention promo with a mix or
  pricing arm was not run, and `promoRebanded` was false here.
- **`spec:mix-card` was not re-run against the button-label change** beyond the
  suite, because the unheld label is byte-identical.
