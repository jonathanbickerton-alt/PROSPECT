## 2. The mechanism — one rule, three carriers

**The three do not differ.** (b) and (c) agree to the penny at all 22 months,
so the promotion's re-banded pool machinery is not engaged by a plain inflow
promotion with no mix and no pricing arm. (a) follows the same rule at its own
scale.

The rule is `newBBase` at `WhatIfTab.tsx:1581`:

```ts
const newBBase = Math.max(0, p_bBase + p_prevBBaseIn - p_prevBBaseOut);
…
p_prevBBaseIn  = m.baseline.inflow;      // :2302, at the END of the loop body
p_prevBBaseOut = m.baseline.outflow;
p_bBase = newBBase;
```

A month's base is rolled from the **previous** month's inflow and outflow, and
those are assigned at the *end* of the iteration — so a row landing in month *k*
cannot reach Base before month *k*+1. **The campaign's own first month reads
`+0.00` in all three runs**, which is that rule showing itself directly.

**Retention's re-banded pool shows no divergence.** EXPECTED.md's recorded rule
(pool feed `2ecdefb`) is that a retention pool feeds Base at T+1 only; run (a)
is consistent with it at every month, and its shape is identical to the two
inflow runs. A held row behaves as an ordinary row of the same volume in the
same month — which is what item 1.4 asked to be true.

## 3. Reconciling 63,000 / 6,300 — the scripts were right

The 2146 and 1651 tables printed `SUM 63,000` and `SUM 6,300` from:

```ts
const vols = shape.map(s => Math.round(3000 * s.fraction));
console.log(… '| SUM', vols.reduce((a,b) => a+b, 0), …)
```

**There is no 23rd row and no double-counted month.** Twenty-two rows are the
three ramp rows plus **nineteen** more at the held figure — and the ramp's own
third row is already at that figure, so there are **twenty** rows at 3,000:

```
ramp 1000 + 2000 + 3000 = 6,000   then 19 × 3,000 = 57,000   →  63,000
1000 + 2000 + 3000×19    = 60,000   ← that is 21 rows, not 22
```

**The brief's expectations of 5,700 and 57,000 are the TAIL ALONE** — 19 × the
held figure — excluding the three ramp rows. Both appear in the tables, at
**2028-05**, one month before the month being read. So the slip is in the
hand-arithmetic, not in the app and not in the earlier scripts.

**Your two card readings, against measurement:**

## 7. Why the measurement hung, and what that costs

Both 03:26 runs **printed every figure and then never exited**. The last line
of `basecard.out` is `2028-06  3000  63000  +60000.00` — the final row of run
(c), i.e. the whole measurement completed.

**The cause is open handles after completion**, not the select setter, not an
await on a worker, and not contention between the two runs: the script has no
`process.exit()`, and JSDOM's window, the two React roots and the
`requestAnimationFrame` stub (a `setTimeout`) all keep the event loop alive
indefinitely.

The earlier `bw335pv9k` run wrote **0 bytes** — it had already crashed on a
different fault (an `HTMLInputElement` value setter applied to a `<select>`)
and was killed at a foreground timeout before printing anything. That is the
better of the two ways to be wrong: it produced no table rather than a wrong
one.

Both tasks were killed and the six leftover node processes ended; **the Vite
dev server (PIDs 35256, 81820) was left alone**, verified by command line
before and after.

**`scripts/.basecard-tmp.tsx` is therefore NOT committed as a spec.** Item 1
allows that only if it is made to exit and to print a report line the suite
runner reads; it does neither yet. It stays untracked, named here, with the
measurement it produced preserved in `scratchpad/basecard.out`.

**And it has now been moved OUT of the repo**, to the scratchpad as
`basecard-tmp.tsx`. CLAUDE.md is explicit that scratch harnesses go to the
scratchpad and never into the repo, because an untracked file in `scripts/`
hides genuinely unexpected entries in `git status` — which is the one place a
later session looks to decide whether a tree is clean. It was left in place
long enough to produce the measurement and no longer.

## Limits

- **One cohort, one save.** Corporate / Mobile Voice on the 20:33 file, a
  24-month horizon, campaigns starting at index 2. The T+1 rule is observed
  here, not proved in general.
- **The promotion run carried no mix and no pricing arm**, so `promoRebanded`
  is false throughout. A re-banded Retention promotion is a different path and
  was not measured.
- **The resolved aggregate reports `seedBaseKnown false`**, so Base is a pure
  delta over an unknown stock; the deltas are unaffected.
- **The measurement script is untracked** and not part of the suite (§7), so
  nothing in the gate re-checks these figures. They are reproducible only by
  re-running that file.
- **Nothing was run against a browser.** The card was read from JSDOM.
- **guard-traps crashed on its first mutation and had to be re-run.** The first
  attempt died at `writeFileSync` on `WhatIfTab.tsx` with `UNKNOWN` /
  `errno -4094` — a Windows lock on open-for-write, the file being watched by
  the running Vite dev server — and **left the file mutated**, because the
  harness restores in a `finally` that never ran. Zero traps executed. The file
  was restored from the scratchpad backup, not with `git checkout`, and its md5
  verified back to `ef0a96421cacc040955a01f0fad6af3f`. The dev server was left
  running: Jon's standing instruction is to leave it alone, and killing it to
  make my own gate convenient is not a call this session gets to make.
- **That crash is a real gap in the harness, not just bad luck.** A mutation
  harness that can die between mutate and restore will eventually leave a
  poisoned tree for the next command, and the only thing that made this
  recoverable was a hand-taken backup. Worth a rider next session: wrap the
  mutate/restore pair so the restore survives a throw.
