## 1. One constant, three readers

New module `src/utils/ingest.ts`:

```ts
export const MAX_UPLOAD_BYTES = 200 * 1024 * 1024;
export const MAX_UPLOAD_MB = MAX_UPLOAD_BYTES / 1024 / 1024;
```

**The MB figure is derived, not re-typed** — the same reason the constant
exists at all.

**Import Save and Import Actuals had no size check whatsoever** before today: a
500MB file dropped on either went straight into `FileReader` and `XLSX.read`.
Both now read the one constant through the one orchestrator. The input drop's
`50 * 1024 * 1024` literal and its sentence are **gone from App entirely**, and
the spec pins that structurally in both directions:

```ts
check('SITES: EXACTLY three ingest paths call runIngest', runs === 3);
check('SITES: the 50MB literal is GONE from App', !app.includes('50 * 1024 * 1024'));
check('SITES: App spells no byte-size limit of its own',
  !/\b\d+\s*\*\s*1024\s*\*\s*1024\b/.test(app));
```

That last one is the zero-occurrence check the brief asked for: it fails on
**any** byte-size literal reappearing in App, not just the old one.

**The refusal names both figures** — `big.xlsx is 250.0 MB. The limit is 200
MB.` The sentence it replaces, *"File size exceeds 50MB limit."*, told a user
neither how big their file was nor, after a limit change, which limit they had
hit.

The boundary is asserted **to the byte**: exactly `MAX_UPLOAD_BYTES` is
accepted, `MAX_UPLOAD_BYTES + 1` is refused.

## 2. The notice, painted before the parse — and the one check that catches it

`runIngest` is control flow, and every line is ordered deliberately:

```ts
const refusal = fileSizeRefusal(p.file, p.t);
if (refusal !== null) { p.onRefuse(refusal); return; }   // read() is never called

p.showNotice(ingestNoticeText(p.file, p.t));
await nextPaint();

const t0 = Date.now();
try { const value = await p.read(p.file); p.onResult(value, Date.now() - t0); }
...
finally { p.showNotice(null); }
```

**A refused file must not reach `read` at all** — not "must not parse
successfully", must not be *called*, because a 300MB file handed to SheetJS is
the freeze the limit exists to prevent. The spec asserts the stub reader's call
count is **0**.

### Why the spec reads the DOM and not the callback log

Trap 213 removes `await nextPaint()`. Under it:

- the callback-order check **stayed green** — `showNotice` still ran first;
- the structural check that `nextPaint` nests two rAFs **stayed green** —
  `nextPaint` itself was untouched;
- and exactly one check reddened:

```
FAIL  ORDER: the notice ELEMENT was in the DOM when the parse began  [false]
```

That is the whole reason the stub reader queries `document` at the moment it
runs rather than trusting the order its own log records. **A claim about a
callback is not a claim about a screen**, and only the second one is the
feature. No source reading of the handler would have found this.

*(I checked the spec was not simply flaky: three consecutive runs on the
restored file, 42/42 each time.)*

## 3. Two frames, not one

```ts
export function nextPaint(): Promise<void> {
  return new Promise<void>(resolve => {
    const raf = (globalThis as any).requestAnimationFrame;
    if (typeof raf === 'function') raf(() => raf(() => resolve()));
    else setTimeout(resolve, 0);
  });
}
```

**A single rAF callback runs BEFORE the paint it is scheduled against**, so a
synchronous parse started there still blocks the frame the notice was supposed
to appear in — the notice would be in the DOM and invisible, which on screen is
indistinguishable from no notice at all. The second rAF runs after that paint
is committed. `setTimeout` is the fallback where there is no rAF and nothing to
paint.

The spec's harness stubs `requestAnimationFrame` as a **real deferred
callback**, not as a synchronous call, deliberately: a stub that fired inline
would remove the thing under test.

## 4. The measured time

```ts
setLoadedLine(loadedLineText(jsonData.length, parseMs, t));
```

`parseMs` is wall time across `read` and nothing else, taken by `runIngest`
from a real clock. The line reads **"Loaded 145,344 rows in 6.4 s"**, and it
exists so the notice's *"up to a minute"* can be replaced by a figure someone
**read** rather than estimated — which is what item 3's fixtures are for and
what trap 214 removes.

## 5. Session-file routing

```ts
export function isSessionWorkbook(sheetNames: readonly string[] | undefined): boolean {
  if (!sheetNames) return false;
  return sheetNames.includes('Metadata') && sheetNames.includes('Market_Events');
}
```

**Both sheets, never either.** `Metadata` alone is a plausible tab name in an
analyst's own workbook, and misrouting an input file into Import Save would
show a user a validation error about sheets they have never heard of.
`Market_Events` is a name this app coined, so the **pair** is what makes the
inference safe. Trap 216 plants the loosening; the spec also pins that matching
is **exact, not case-folded**.

**On the cost, stated honestly at the line.** Decision 3 asks for names read
before the full parse "where the reader allows". On the input path it does not
help: a non-session file must be parsed regardless, so the sniff reads
`wb.SheetNames` from the workbook this path has already read. A
`{ bookSheets: true }` pre-read would be ~4ms against a 766ms full parse (1147
report) and is the right shape for a path that can *refuse* before parsing —
this one cannot. **"Reads names only" and "costs nothing extra" are two
different claims and only the first is true here**, so the comment says so.

**Routing does not re-read the file.** `applyImportSaveWorkbook` was extracted
out of `handleImportSaveFile`'s FileReader callback so the workbook can be
handed over as an argument — re-opening would parse up to 200MB twice, on the
one thread the notice exists to apologise for.

## Limits

- **The mount is at the seam, not at App.** `src/App.tsx` is mounted by no spec
  in this repo, so decision 2's ordering could not be asserted inside a handler
  there at all — extracting `runIngest` is what made it testable. That the
  three handlers call it is pinned **structurally** (`runIngest<` occurs
  exactly three times), not by driving App's own file inputs.
- **No browser was used.** The rAF behaviour is reasoned from the spec of
  requestAnimationFrame and asserted in JSDOM with a deferred stub; the claim
  that two frames are needed for a *paint* is not verified against a real
  compositor. Jon's runs on the fixtures are what will confirm the notice
  appears.
- **The success-line time is 0.0 s in the spec**, because the stub reader
  returns instantly. The assertion is that the line carries a seconds figure at
  all; the real figures come from item 3.
- **The refusal on Import Actuals is an `alert()`**, matching that path's
  existing error handling rather than introducing a banner it has never had.
- **`Import Save`'s refusal renders through `importSaveResult`**, its existing
  channel, so a refused save file reports in the same place a malformed one
  does.
- **Nothing measures a 200MB file end to end in this session.** The limit rests
  on the 1147 report's Node measurements plus the notice; the browser figures
  are Jon's to take.
